# Dropping the Python models: what we gained and lost

- **Date:** 2026-11-03
- **Branch:** `v0.1-schema`
- **Decision:** D7 of `2026-11-03-v0.1-schema-design.md`: the package ships only
  artefacts (the LinkML sources, the generated JSON Schemas and the record's
  JSON-LD context), with no generated Python and no runtime dependency.

## In one paragraph

astra-spec used to ship two Python models generated from the schema
(dataclasses and pydantic). The only real use of them was as a structural
validator, and as a validator they were weaker than the JSON Schema we now
treat as the contract. They ignored LinkML's rules, never checked map keys,
and didn't match the YAML they validated. Dropping them makes the JSON Schema
the one definition of a valid file, and Python and JavaScript validators agree
on it. What we give up is typed Python objects and a ready-made Python API,
which nothing uses today. A tool that wants them can generate them from the
JSON Schema itself.

## What the models were used for

Checked on 2026-11-03 against the local checkouts:

| Consumer | How it used the models |
|---|---|
| **astra-tools** | Three calls, all in `validation/schema.py`: `Analysis.model_validate`, `Output…`, `Universe.model_validate`, as the structural check. Nothing builds model objects or reads their attributes: astra-tools is dict-based by design. Separately, it uses `astra.datamodel.SCHEMA_DIRECTORY` (a path constant, in 3 places) and LinkML's `SchemaView` for `astra spec`, which goes through LinkML, not pydantic |
| **lightcone-cli** | None directly. It depends on `astra-tools==0.2.18` and calls its functions (`astra.validation.validate_analysis_schema`, `astra.helpers`, `astra.resolve`, `astra.scaffold`). So it runs the pydantic check indirectly, through astra-tools. Its own `pydantic` dependency is for its own configuration (compute catalogues, execution resources), not ASTRA documents |
| **astra-spec's own tests** | The dataclasses, to load valid fixtures |
| **lightcone-docs** | None. It pulls in the npm package `@astra-spec/ui` (the TypeScript side), which didn't use the Python models |

## What the models did badly

- **Rules ignored.** LinkML's pydantic generator doesn't enforce `rules` or
  `exactly_one_of`. astra-tools had to re-implement checks such as "exactly one
  of `doi` and `artifact`" in its semantic layer.
- **Map keys unchecked.** A decision called `Not-A-Valid-Id!` passed.
- **A different shape from the YAML.** The models expect `id` inside each
  entry, so astra-tools copied every map key into its entry before validating
  (`_inject_ids_inplace`).
- **Slow to import.** astra-tools' own docstring measures importing
  `astra.datamodel` at about 200 ms, more than the rest of astra together.
- **Untested against the contract.** The published JSON Schema rejected
  `main`'s own valid fixture and the iris example, and nobody noticed, because
  the valid fixtures went through the dataclasses instead.

## What we lose

1. **Typed Python objects** (`analysis.outputs["f1"].format`, with
   autocompletion and mypy). Nothing uses them today; a future Python tool or a
   notebook user might want them.
2. **A ready-made Python API from astra-spec.** `from astra.datamodel import
   Analysis` no longer exists, so code importing it breaks. Locally that is
   only astra-tools (above); third parties weren't checked.
3. **Building documents in code.** A tool that writes `astra.yaml` (a scaffold,
   an editor, a runner writing records) builds plain dicts and validates them,
   rather than constructing typed objects.
4. **The other LinkML outputs.** `gen-project` (OWL, SHACL, Java, LinkML's own
   TypeScript) is gone. Its output was never committed or shipped, so nothing
   could depend on it.
5. **A ready mapping from errors to rule codes.** A JSON Schema error names the
   keyword that failed (`required`, `pattern`) and where, not the catalogue code
   (`MISSING_FIELD`, `INVALID_COMMIT`). Today the mapping exists only inside
   astra-spec's tests (`tests/conftest.py`), so each tool would reimplement it.
   See *The open question* below.

## What we gain

- **One definition of validity.** The committed JSON Schema is the contract.
  Every fixture gets the same verdict from Python's `jsonschema` and from Ajv
  (JavaScript), the latter compiling it in strict mode.
- **More checked, earlier.** Map keys, one written form per entry, no `null`,
  no duplicate list entries, exactly-one-of rules, and every pattern behaving
  the same in Python and JavaScript.
- **A lighter package.** No runtime dependencies; quicker imports.
- **Reviewable changes.** Every change to what is valid shows as a diff of a
  committed file, and a drift check stops the file and its sources diverging.
- **No mismatch to work around.** No id injection, and no gap between what the
  schema says and what the models enforce.

## How astra-tools adapts (the tooling phase)

- **Structural check:** `jsonschema.Draft201909Validator` over
  `importlib.resources.files("astra.schema") / "generated/analysis.schema.json"`.
  `_inject_ids_inplace` and the pydantic import go.
- **YAML loading:** a loader for YAML 1.2's core schema only, as in
  astra-spec's test harness, so astra-tools, the tests and a JavaScript tool
  read a file the same way.
- **Schema files:** the three `SCHEMA_DIRECTORY` uses read the files through
  `importlib.resources`.
- **Semantic checks:** these move to maps keyed by id, addresses, in-file
  universes and declarations, and report the catalogue's codes. This is most of
  the work, and it comes from the RFCs, not from dropping the models.
- **Typed objects, if wanted,** belong in astra-tools. They can be generated
  from the JSON Schema (for example with datamodel-code-generator, for pydantic
  v2), and built only after a document passes JSON Schema validation. They are
  then a convenience that can't disagree with the contract.
- **lightcone-cli** keeps calling the same astra-tools functions. It needs no
  change of its own beyond moving to the new astra-tools release.

## How astra-typescript adapts

Not checked: its code isn't in this workspace. The usual route:

- **Types** come from the JSON Schema with `json-schema-to-typescript`.
  Id-keyed maps become `Record<string, Output>`, and `Universe.decisions`
  becomes `Record<string, string>`.
- **Validation** uses Ajv, which compiles the contract in strict mode.

Pruning the unreachable definitions and allowing one form per map entry mean
the generated types have no duplicate, id-bearing shapes.

## The open question: a machine-readable rule catalogue

The one real gap is item 5 above. A tool reporting the catalogue's codes has to
turn each JSON Schema error into a code, and every tool should do it the same
way.

A table from JSON Schema keyword to code isn't enough, because a keyword can
stand for several codes. A `pattern` failure is `INVALID_ID`,
`INVALID_REFERENCE`, `INVALID_COMMIT`, `INVALID_PATH`, `BLANK_EXCLUDED` or
`INVALID_VALUE`, depending on the field. So the mapping has to go by *where* in
the schema the error comes from (its schema path, which both Python's
`jsonschema` and Ajv report). The generator knows each slot's range and
constraint, so it could write that mapping out.

Status: **decided 2026-11-03 (D13).** `generated/rules.json` is derived:
the rules are extracted from the specification's §9, which stays the
hand-written source, as CommonMark extracts its tests from its spec and the
W3C's webref extracts definitions from specs; the error map comes from the
schema, where each constraint names the rule it enforces, keyed by the error's
absolute keyword location. The tests read the same file. Considered and not
chosen: a hand-written data file with §9 generated from it (the linter
pattern, where the tool is the authority), and codes on the constraints only,
with no extracted catalogue (each tool would then word and link every rule
itself).
