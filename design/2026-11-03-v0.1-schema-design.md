# v0.1 schema: design

- **Date:** 2026-11-03
- **Branch:** `v0.1-schema`, from `main` at `1bc6eb8`
- **Status:** implemented on `v0.1-schema`

## 1. Goal and scope

**Goal.** One schema, one contract and one specification for ASTRA v0.1 that
implement RFCs 0003–0007 and the draft *Schema tidy-up* RFC exactly, with every
rule enforced as high up as it can be.

**In scope**

- the LinkML schema (`src/astra/schema/`)
- the generated JSON Schema, which is the contract (§3)
- the normative `docs/specification.md`
- the schema-layer tests (§9)
- `examples/iris` and `examples/iris_pipeline`, migrated (they double as valid
  fixtures)
- RFCs 0003, 0004, 0005, 0006, 0007, the tidy-up draft, and the two tidy-up
  items pending at the start of this work: the FragmentSelector swap and
  `Analysis.version` → `spec_version`

**Out of scope**

- `when` (#93): `when` keeps the meaning it has on `main`
- citing insights: `Option.insights` keeps its meaning
- recipes: `Recipe`, `Resources` and both `container`s are untouched
- every other docs page (`index.md`, `getting-started.md`, `cli.md`,
  `llms.txt`, `README.md`). They will be stale on this branch, and a failing
  docs build is expected for this phase
- tooling (astra-tools, typescript-astra) and the validator, check and runner
  conformance suite (§12)

**Done means**

- the schema implements every statement of the in-scope RFCs, shown by the
  traceability checklist (§10)
- every rule sits in the highest layer that can enforce it (§7)
- every valid and invalid fixture passes or fails through the published JSON
  Schema, failing where it says it fails
- the specification is enough to build a validator, checker or runner from
  without reading the RFCs

**Approach.** A clean rewrite against the traceability checklist, not one RFC
at a time: later RFCs undo earlier forms (0004 replaces 0003's
`Universe.analyses`, 0006 replaces 0004's inputs, tidy-up flips lists to
maps), so each rule is written once, in its final form.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The generated JSON Schema is the contract. LinkML is the source we edit | Language-neutral (astra-tools, typescript-astra, editors through `yaml-language-server`) and published at `w3id.org/astra`. It is what LinkML's own `linkml-validate` uses by default ([Validating data](https://linkml.io/linkml/data/validating-data.html)), and it has the highest feature coverage of LinkML's generators on the project's [dashboard](https://linkml.io/linkml/generators/dashboard.html): 62% of 66 feature tests fully implemented, against 47% for Pydantic, including the precondition rules, `value_presence`, `exactly_one_of` and dict inlining this design depends on. Its weaker rows (`unique_keys`, keys, the regex dialect) are where D3's extension and the fixtures compensate. LinkML has no official tiering of generators ([governance](https://linkml.io/linkml/maintainers/generator-governance.html)) |
| D2 | Everything referenced by id is a map keyed by id. A list is used only for what is a list (`evidence`, a record's `inputs`, and lists of strings) | One principle. Uniqueness is structural (duplicate keys are invalid YAML 1.2), and the id is written once. Order carries no meaning in any keyed collection |
| D3 | A small extension of LinkML's JSON Schema generator adds `propertyNames` to every id-keyed map and allows one written form per map entry | Stock LinkML 1.12.1 checks neither map keys nor the form of map values (probe, §3) |
| D4 | Element ids are LinkML `key`s, not `identifier`s. The only `identifier` is `Environment.iri` | A key is unique within its container, which is what author-given ids are. An identifier is globally unique, which only things named by the world are. As RDF, `identifier`s merged unrelated elements (`astra:none`) |
| D5 | One id grammar, `[a-z][a-z0-9_]*`, everywhere. The reserved-word list goes. Ids that one field could resolve to are distinct | After RFC 0004, an address's kind comes from the field it's written in, so category words can't shadow anything. The one real ambiguity is two kinds one field takes (today an input and an output, through `Output.inputs`). JSON Schema can't relate the keys of two maps, so it is a validator rule (`AMBIGUOUS_ID`), worded generally so that it covers any field that later takes more than one kind. Merging `inputs` and `outputs` into one map was considered and rejected: it costs the inputs/outputs vocabulary to save one simple rule |
| D6 | `Analysis.id` is removed | Nothing references it: declarations name analyses locally, results go by address, and identity is commit plus path (RFC 0007) |
| D7 | The package ships only artefacts: the LinkML sources, the generated JSON Schemas and the record's JSON-LD context. No generated Python and no runtime dependency | Nothing in the package can disagree with the contract. The pydantic models enforce neither `rules` nor `propertyNames`, and needed their ids injected |
| D8 | Fields are defined in LinkML (descriptions are their normative text, and the field reference is generated). The specification carries concepts, grammars and the rule catalogue, and links to the reference | One statement of each fact, so the two can't drift |
| D9 | A normative rule catalogue: each rule has a code, a layer, a level (`MUST`/`SHOULD`/`MAY`), one statement of what holds and a source, all written one way (§7) | Machine-checkable later by a conformance suite (§12) |
| D10 | The record's `version` becomes `spec_version`. The record schema ships closed, plus a generated open variant for checkers reading newer records | The same name for the same concept. RFC 0005 wants both "only its version's fields" and "ignore unknown fields", which takes two schemas |
| D11 | A named type exists only if more than one field uses it. A pattern used once is written on its field | Keeps `types.yaml` to the grammars the format is built from |
| D12 | Optional fields don't accept `null` | One way to write a file |
| D13 | A machine-readable catalogue, `rules.json`, is derived, never written by hand: the rules (code, layer, level, statement, source, status) are extracted from the specification's §9, which stays the hand-written source; the error map (where in a JSON Schema an error comes from → its code) is derived from the schema, where each constraint names the rule it enforces | The specification-body practice (CommonMark extracts its tests from its spec; the W3C's webref extracts IDL and CSS from specs; a malformed extract is a spec bug). Every tool then maps errors to the same codes and shows the same wording, and the tests read the same file as the tools |

## 3. Architecture and artefacts

### Sources (`src/astra/schema/`, hand-written)

| Module | Holds | Imports |
|---|---|---|
| `types.yaml` | The named types of §4, with the grammar pieces in `settings` so the `structured_pattern`s are built from them | `linkml:types` |
| `analysis.yaml` | Root of `astra.yaml` (`tree_root: Analysis`): Analysis, AnalysisDeclaration, Input, Output, Recipe, Resources, Decision, Option, Universe, DecisionSelection, OutputType | `types`, `insight` |
| `insight.yaml` | Insight, Evidence, TextQuoteSelector, FragmentSelector | `types` |
| `provenance.yaml` | Root of a record (`tree_root: ProvenanceRecord`): ProvenanceRecord, Generation, RecordedInput, Environment, Runner, with PROV-O mappings | `types` |

`universe.yaml` folds into `analysis.yaml`. It was separate only because
universes lived in files of their own.

### Generated (`src/astra/schema/generated/`, committed)

| File | Root | Generator options | `$id` |
|---|---|---|---|
| `analysis.schema.json` | Analysis | closed, `--no-include-null` | `https://w3id.org/astra/0.1/analysis.schema.json` |
| `provenance.schema.json` | ProvenanceRecord | closed, `--no-include-null` | `https://w3id.org/astra/0.1/provenance.schema.json` |
| `provenance.open.schema.json` | ProvenanceRecord | `--not-closed`, `--no-include-null` | `https://w3id.org/astra/0.1/provenance.open.schema.json` |
| `provenance.context.jsonld` | | LinkML's context, post-processed by `tools/jsonld_context.py` |
| `rules.json` | | `tools/rules.py` (D13) |

- **Built by** `just gen-schema`, which runs the extension (below) for the
  three JSON Schemas and `tools/jsonld_context.py` for the record's context.
- **Committed** so that every change to the contract is a diff in review and
  building the package needs no LinkML. A test regenerates them and fails on
  any difference.
- **Versioned at release.** Sources keep the placeholder `version: 0.0.0`, and
  `just release` regenerates the artefacts with the release version, then
  commits them regenerated as `dev` after the tag. A build stamps the tag at
  HEAD, or `dev` between releases and in a clone without tags. The version's
  series goes in each `$id`: `X.Y` for a release `X.Y.Z`, a pre-release's
  whole version (`0.1.0rc1`), or `dev`. A patch release never changes what is
  valid, so `just release` compares a patch's regenerated schemas and error
  map with its minor version's greatest release (`tools/check_patch.py`).
- **The field reference** (`docs/elements/`) comes from `gen-doc`, run over
  both roots (`analysis.yaml` and `provenance.yaml`), as part of the docs build.
- **Each JSON Schema's `$id`** is the URI of its own file under its minor
  version (table above), so the closed and open record schemas are distinct
  resources, and so are two minor versions held side by side. The patches of
  one minor version share it (spec §1, §10).
- **Only standard keywords at the top level:** LinkML's `metamodel_version` is
  dropped and the schema version moves into `$comment`, so strict validators
  (Ajv) compile the contract.
- **`rules.json`** (D13) holds `rules`, one entry per catalogue code (`code`,
  `layer`, `level`, `statement` as the cell's inline Markdown with links
  reduced to their text, `source`, and `status` for the check layer), and
  `errors`, a map from a JSON Schema error's absolute keyword location (the
  schema's `$id`, `#`, and a JSON Pointer to the failing keyword, e.g.
  `https://w3id.org/astra/0.1/analysis.schema.json#/$defs/AnalysisDeclaration/properties/commit/pattern`)
  to its code. The rules are parsed from §9 with a Markdown parser, never by
  regular expressions, and extraction is strict: a malformed row, a duplicate
  code, an unknown layer or level, or a statement whose keyword contradicts
  its level fails the build. Each constraint in the LinkML sources names its
  code (an annotation on the type, slot or class rule); only keywords whose
  code never varies take a default: `required` outside a rule;
  `additionalProperties`; `type` (`WRONG_TYPE`), except on a map key, which
  takes the key's code; `minProperties`/`minItems` of 1 (`EMPTY_COLLECTION`);
  `uniqueItems`; `enum`; `minimum`. Every constraint in the generated schemas
  has a code, and every code the schema names is a parse/schema code of §9.
  Fixtures are not listed in `rules.json` (they aren't shipped); a test links
  them to the catalogue.
- **No JSON-LD context for `astra.yaml`** (Ruling R18). LinkML's flat context
  gives a wrong RDF reading of id-keyed maps (an entry's key becomes a
  predicate) and merges terms that share a name (`decisions`). A faithful
  context (`@container: @id`, scoped contexts) is later work. The record's
  context maps its terms onto PROV-O. A record's RDF is what JSON-LD 1.1's
  toRdf gives with it, plus each node's class URI as its `rdf:type` (spec
  §10), not LinkML's RDF conversion, which reads any value without `://` as
  a CURIE and fails on a `urn:` IRI.
- **The record's context is prefix-free.** Stock `gen-jsonld-context`
  declares `astra`, `linkml`, `prov`, `schema` and `xsd` as simple terms
  ending in `/` or `#`, which JSON-LD 1.1 makes prefixes, so an environment
  `iri` such as `prov:env:1` would become `http://www.w3.org/ns/prov#env:1`.
  `tools/jsonld_context.py` takes LinkML's context, drops those terms after
  writing every `@id` and `@type` as a full IRI, and adds `"@version": 1.1`,
  so that a JSON-LD 1.0 processor, which reads any term as a prefix, rejects
  it. No term is a prefix, so every `iri` is read exactly as written.

### The generator extension

- **What it is:** one dev-only module, `tools/jsonschema_generator.py`,
  subclassing LinkML's `JsonSchemaGenerator`. Everything else is stock LinkML,
  pinned at `linkml==1.12.1` as a dev dependency.
- **What it does,** for every multivalued slot inlined as a dict:
  1. adds `propertyNames` with the key slot's type (its `pattern`)
  2. allows one written form per entry:
     - **object form only** (`seed_42: {}`): removes LinkML's string and null
       alternatives, and removes the key slot from the entry's object, so the
       id is written once, as the key (`seed_42: {id: seed_42}` fails)
     - **compact form only** when the class has its key and exactly one other
       slot: the value is that slot's type. In this schema that's only
       `DecisionSelection`, so `Universe.decisions` is `model: svm`
  3. emits `uniqueItems: true` on every multivalued slot of scalars (lists of
     strings), so no list holds the same entry twice
  4. drops `$defs` the root can't reach, and the non-standard top-level
     keywords (above)
- **And for every class-level check** (an `exactly_one_of`, a class rule):
  5. moves it into its own member of `allOf` (the `exactly_one_of` first, then
     the rules), guarded by the types of what it reads:
     `{if: G, then: {oneOf: […]}}`, and `{if: G + the rule's if, then: the
     rule's then}`, where `G` is `{type: object, properties: {f: {type: <f's
     JSON type>}}}` over the fields `f` the check reads. A check is skipped
     only where a `type` keyword already fails, so no verdict changes, and a
     value of the wrong type is `WRONG_TYPE` alone. Each `required` in a check
     gets its fields in a `properties` beside it, inside a `not` too, so that
     Ajv compiles the schema under `strict: true` (`just check-ajv`, in CI)
- **Why it's needed** (a probe with LinkML 1.12.1, on `main`'s schema and a
  scratch schema):
  - map keys aren't checked at all: a decision `Not-A-Valid-Id!` passes
  - map values also take `"label"` and `null`
  - a class-level check only tests whether a key is there: a declaration
    written as a string, or `url: null` beside `path`, also gets
    `INVALID_DECLARATION_SOURCE` or `URL_WITHOUT_COMMIT` beside its
    `WRONG_TYPE`; and LinkML writes a field that must be absent with its
    `properties` beside the `not`, which Ajv's `strictRequired` rejects
  - `main`'s published JSON Schema rejects `main`'s own valid fixture and
    `examples/iris`: the rule `label_and_options_required_when_not_aliased`
    turns `options` into an array check. The tests missed it because valid
    fixtures went through the dataclasses, not the JSON Schema
- **Upstream.** Both behaviours are general, so the module is written to be
  offered to LinkML as a whole.

### Package

- **The wheel** holds `astra/schema/`, the sources and `generated/`, as the
  namespace package `astra.schema`, found through `importlib.resources`.
  `requires-python` is the lowest version where that works for namespace
  packages: **3.10** (tested: 3.9 fails, 3.10 and 3.11 work).
- **Dependencies:** none.

### Removed

- `src/astra/datamodel/` (the dataclasses and the pydantic models)
- `src/astra/schema/universe.yaml`
- the `gen-python`, `gen-project` (Python) and `_fix-python-keywords` recipes
- the `from:` → `from_:` rewrite in `tests/test_data.py`
- the `linkml-runtime` dependency

## 4. Names and grammars

### Grammar (for the specification, ABNF per RFC 5234)

```abnf
id               = lower *( lower / DIGIT / "_" )
lower            = %x61-7A                      ; a-z
address          = id *( "." id )               ; [declaration "."]... element
reference        = address [ "#" id ]           ; "#" pins a universe
option-reference = address "." id              ; a decision's address, then an option id
condition        = [ "~" ] option-reference     ; "~": the option is not selected
```

The last segment of an `option-reference` is always the option, so a decision
of a declared analysis is `iris.random_seed.seed_42`.

### Named types (`types.yaml`)

| Type | Pattern | Used by |
|---|---|---|
| `id` | `^[a-z][a-z0-9_]*$` | every map key but those of `Universe.decisions`; also `Universe.derived_from`, `Option.insights` and the values of `Universe.decisions` |
| `address` | `id` joined by `.` | `Output.decisions`, the keys of `Universe.decisions` |
| `reference` | `address`, optionally `#` `id` | `Output.inputs`, `Evidence.artifact`, `ProvenanceRecord.address`, `RecordedInput.entry` |
| `option_reference` | `address` `.` `id` | `Option.requires`, `Option.incompatible_with` |
| `condition` | optional `~`, then `option_reference` | `Output.when`, `Decision.when` |
| `commit_id` | `^([0-9a-f]{40}\|[0-9a-f]{64})$` | `AnalysisDeclaration.commit`, `Generation.commit` |
| `content_hash` | `^sha256:[0-9a-f]{64}$` | `ProvenanceRecord.content_hash`, `RecordedInput.content_hash` |
| `spec_version` | `MAJOR.MINOR.PATCH`, no leading zeros | `Analysis.spec_version`, `ProvenanceRecord.spec_version` |
| `timestamp` | `YYYY-MM-DDThh:mm:ss.sssZ`, each field in its range (month 01–12, day 01–31, hour 00–23, minute and second 00–59); RDF datatype `xsd:dateTime` | `Generation.started`, `Generation.finished` |
| `iri` | an IRI (RFC 3987): a scheme, `:`, then RFC 3987's characters, `%` only before two hex digits and at most one `#`, `^[A-Za-z][A-Za-z0-9+.-]*:(C\|%[0-9A-Fa-f]{2})+(#(C\|%[0-9A-Fa-f]{2})*)?$` with C `` [^\x00-\x20\x7f-\x9f<>"{}\|\\^`%#\u200e\u200f\u202a-\u202e] `` (no ASCII space, ASCII control or C1 control, and none of the bidi formatting characters RFC 3987 §4.1 forbids: U+200E, U+200F, U+202A–U+202E). `typeof: string`, never `uri`, whose `format: uri` Ajv strict rejects; the structure is unchecked (§13) | `Environment.iri`, `FragmentSelector.conforms_to` |

`id`, `address`, `reference`, `option_reference` and `condition` are
`structured_pattern`s built from one `id` setting, so the id grammar is
written once.

**Every `$` outside a lookahead is written `$(?!\n)`, every anchored pattern
ends in one, and no pattern uses `.`, `\s`, `\S`, `\d`, `\w` or `\b`.**
Python's `re`, which Python JSON Schema validators use, lets `$` match
before a final newline, and ECMA-262's `$` doesn't. Without the lookahead
`"a\n"` (a YAML block scalar gives one) would be a valid `id` in Python and
invalid in JavaScript. The
shorthand classes differ in the same way (Python's `.` matches `\r`, its `\s`
includes `\x1c`–`\x1f`), so patterns use explicit classes: `[0-9]`,
`[^\x00-\x20\x7f]` for a character other than an ASCII space or control,
`[^\x00-\x1f\x7f]` for any character but an ASCII control, and
`[^\x00-\x20\x7f-\x9f]` and `[^\x00-\x1f\x7f-\x9f]` for the same two
without the C1 controls (U+0080–U+009F). The patterns below are written in
the short form, for readability.

Above U+007F a class leaves out only what it names, so six fields admit
characters that aren't visible (spec §4; §11 item 21):

| Field | Class | Admits above U+007F |
|---|---|---|
| `Option.excluded`, `AnalysisDeclaration.url` | `[^\x00-\x20\x7f]` | every character: non-ASCII spaces (U+00A0, U+3000), format characters (U+200B, U+FEFF, U+202E), U+2028/U+2029 and the C1 controls |
| `FragmentSelector.value` | ``[^\x00-\x20\x7f"#%<>\[\\\]^`{\|}]``, or `%` and two hex digits | every character, as for `Option.excluded` |
| `Evidence.doi`, its suffix | `[^\x00-\x20\x7f-\x9f]` at either end, `[^\x00-\x1f\x7f-\x9f]` inside | every character above U+009F: non-ASCII spaces anywhere, which are graphic and so legal in a DOI, and format characters, U+2028/U+2029, private use and noncharacters, which ISO 26324 doesn't allow (it takes Unicode's graphic characters) |
| `iri` (`Environment.iri`, `FragmentSelector.conforms_to`) | `` [^\x00-\x20\x7f-\x9f<>"{}\|\\^`%#\u200e\u200f\u202a-\u202e] `` | every character above U+009F but the bidi controls RFC 3987 §4.1 forbids: non-ASCII spaces, the other format characters (U+200B, U+FEFF) and U+2028/U+2029, which RFC 3987's `ucschar` holds, and the characters outside it (§13) |

### Patterns used once (inline, on their field)

| Field | Says |
|---|---|
| `Output.format` | a lowercase token, `^[a-z0-9][a-z0-9_.+-]*$` (as on `main`) |
| `Input.path` | relative, `/`-separated, no `..` segment, not ending in `/` |
| `AnalysisDeclaration.path` | relative (no leading `/` or `~`); `..` allowed |
| `Option.excluded` | not blank: holds a character of the class `[^\x00-\x20\x7f]` (above) |
| `Evidence.doi` | a DOI name (ISO 26324) in the `10` directory: `10.`, a registrant code of digit runs joined by `.`, `/`, then a suffix with no control character (C0, DEL or C1) and no ASCII space at either end, `^10\.[0-9]+(\.[0-9]+)*/[^\x00-\x20\x7f-\x9f]([^\x00-\x1f\x7f-\x9f]*[^\x00-\x20\x7f-\x9f])?$`. It accepts ISBN-As (`10.978.8889637/173`) and spaces inside the suffix; it rejects a shortDOI (`10/aabbe`) and any other directory indicator (`11.1/x`) (§11) |
| `FragmentSelector.value` | the characters of a fragment identifier, `%` only before two hex digits, ``^([^\x00-\x20\x7f"#%<>\[\\\]^`{\|}]\|%[0-9A-Fa-f]{2})+$`` (no ASCII space or control, none of ``"#<>[\]^`{\|}``); its syntax, the one `conforms_to` names or else a PDF fragment (RFC 8118), isn't checked |

`AnalysisDeclaration.url` takes one of git's two remote forms:
`scheme://…` (`https://github.com/owner/analysis`, `ssh://git@host/x.git`,
`file:///srv/repo`) or scp-like `[user@]host:path` (`git@github.com:owner/repo`),
with the pattern `^(?:[A-Za-z][A-Za-z0-9+.-]*://[^\x00-\x20\x7f]+|(?![A-Za-z][A-Za-z0-9+.-]*://)(?:[^\x00-\x20\x7f/@:]+@)?[^\x00-\x20\x7f/@:]+:[^\x00-\x20\x7f]+)$(?!\n)`.
A value that starts `scheme://` must have something after `://`.
A `url` holds no ASCII space or control character, though git fetches a
remote with a space: a space is written `%20` in a `scheme://` URL, which git
decodes, and since git doesn't decode the scp-like form,
`[user@]host:my dir/x` is written `ssh://[user@]host/~/my%20dir/x` (§11
item 21).
A bare word or a local path (`a`, `owner/repo`, `../repo`) fails:
an analysis in the declaring analysis's repository is declared by `path`,
and another repository on this machine by an explicit `file://` URL.
Whether the URL leads to a valid ASTRA project is the
validator's (`REMOTE_UNREACHABLE`, `MISSING_DECLARED_ANALYSIS`,
`DECLARED_ANALYSIS_INVALID`).

## 5. The analysis document

Every element of `astra.yaml` named by the author is an entry of a map keyed
by its id (D2, D4). "Map" below means that.

### `analysis.yaml`

| Class | Fields | Removed |
|---|---|---|
| **Analysis** | `spec_version` (required), `label`, `description`, `tags`, `inputs` (map of Input), `outputs` (map of Output, required, at least one), `decisions` (map of Decision), `analyses` (map of AnalysisDeclaration), `universes` (map of Universe), `prior_insights`, `findings` (maps of Insight), `container` (untouched) | `id`, `name`, `version`, `path`, inline sub-analyses |
| **AnalysisDeclaration** | `path`, `url`, `commit`. Exactly one of `path` and `url` (`exactly_one_of`); `url` requires `commit` (rule) | – |
| **Input** | `label`, `description`, `tags`, `path` (required) | `type`, `source`, `ref`, `ref_version`, `use_outputs`, `from`, and its rules |
| **Output** | `label`, `description`, `tags`, `type` (required, OutputType), `format` (required), `inputs` (list of `reference`), `decisions` (list of `address`), `when` (list of `condition`), `recipe` | `from`, and its rules |
| **Recipe**, **Resources** | untouched, except that `command`'s description gives the placeholders as RFCs 0003/0004 write them (`{inputs.<entry>}` with the entry exactly as written, dots and `#` included) | – |
| **Decision** | `label`, `rationale`, `tags`, `when`, `options` (map of Option, required, at least one) | `default`, `from`, and its rules |

| **OutputType** | `metric`, `figure`, `table`, `data`, `report` | – |
| ~~KeyValuePair~~, ~~InputType~~, ~~UniverseNode~~ | – | removed |

### `insight.yaml`

| Class | Fields | Removed |
|---|---|---|
| **Insight** | `label`, `claim` (required), `description`, `evidence` (list of Evidence, required, at least one), `scope`, `tags` | `created_at`, `derived`, `notes` (now `description`) |
| **Evidence** (a list item) | `doi`, `artifact` (`reference`), `version` (integer ≥ 1), `quote` (TextQuoteSelector), `location` (FragmentSelector). Exactly one of `doi` and `artifact`; `version` only with `doi` | `id`, `snapshot`, `source_commit` |
| **TextQuoteSelector** (`oa:TextQuoteSelector`) | `exact` (required, `oa:exact`), `prefix` (`oa:prefix`), `suffix` (`oa:suffix`) | – |
| **FragmentSelector** (`oa:FragmentSelector`) | `value` (required, `rdf:value`) and `conforms_to` (`dcterms:conformsTo`, an `iri`): a fragment in the syntax `conforms_to` names, a PDF fragment (RFC 8118, `page=6`) when it is absent | `page` |

`conforms_to` is optional (tidy-up change 4); without it the syntax is
PDF's, so a location written before it keeps its meaning. Web Annotation
names that syntax by the RFC 3778 IRI, and writing that IRI means the same as
writing none. With both a `quote` and a `location`, the quote is sought within
the location (`oa:refinedBy`).

## 6. The provenance record

| Class | Fields | PROV-O |
|---|---|---|
| **ProvenanceRecord** | `spec_version`, `address` (`reference`), `content_hash`, `size` (integer ≥ 0), `generated_by` (Generation), all required | `prov:Entity`, standing for the result; `generated_by` is `prov:wasGeneratedBy` |
| **Generation** | `commit`, `environment`, `runner` (required); `inputs` (list of RecordedInput); `started`, `finished` (`timestamp`, optional) | `prov:Activity`; `inputs` and `environment` are `prov:used`, `runner` is `prov:wasAssociatedWith`, and the times are `prov:startedAtTime`/`prov:endedAtTime` |
| **RecordedInput** | `entry` (`reference`), `content_hash`, `size`, all required | `prov:Entity` |
| **Environment** | `iri` (required, the class's `identifier`, an `iri`, never a CURIE) | `prov:Entity`, the `@id` of which is the IRI exactly as written |
| **Runner** | `id`, `version` (required) | `prov:SoftwareAgent`; `version` is `schema:softwareVersion` |

- `spec_version`, `address`, `content_hash`, `size`, `commit`, `entry` and
  `runner.id` are `astra:` terms, since PROV has none.
- Read as RDF (spec §10), the root node stands for the result, which the run
  generated: its `address`, `content_hash` and `size` describe the result, and
  its `spec_version` describes the record (§12: a `prov:Bundle` would separate
  the two).
- `inputs` is required when the output lists inputs. That depends on
  `astra.yaml`, so it's a check rule (§7), not a schema rule.
- `inputs` stays the list RFC 0005 gives: one item for each entry the output
  lists in the `astra.yaml` files at the record's `commit`, and no other item,
  matched by `entry`; their order carries no meaning (`MISSING_RECORD_INPUTS`).
  A later change to the list makes the result `stale`, not `missing` (RFC 0005
  §4).
- `commit` is the commit the recipe ran from, the driver's commit for what a
  driver's universes build (RFC 0007 §7). It pins every `astra.yaml`, an
  analysis from a commit through its declaration's `commit`.
- A checker reads records only through planned results: a record at no
  planned result's place gets no status, and no check rule applies to it
  (RFC 0005 §4).

## 7. Validation layers and the rule catalogue

### Layers

| Layer | Enforced by | Sees |
|---|---|---|
| **parse** | a YAML 1.2 loader under the core schema, plus §3's checks (`astra.yaml`), or a strict JSON parser (records, §3) | one file's bytes |
| **schema** | the generated JSON Schema | one file's data |
| **validator** | a semantic validator | every `astra.yaml` of the analysis stack, and git (spec §3); no results |
| **check** | a results checker | every `astra.yaml` of the analysis stack, now and at each record's commit, and git (spec §3); records and results |
| **runner** | whatever runs recipes | its own actions |

### How a rule is written

**The rule is always what must (or should, or may) hold. What you get when it
is broken is always in a column of its own.** This is true in every layer:

- **Rule:** one sentence saying what holds in a conforming file, record or
  run. It is in the present tense, and its subject is what the rule is about
  ("A declaration has …", "Every pin names …", "No output …"). It never says
  what happens when it is broken.
- **Level:** `MUST`, `SHOULD` or `MAY` (RFC 2119), applied to that sentence,
  and `MAY` only in the runner table.
- **Code:** names what is wrong when the rule is broken. It is what a tool
  reports.
- **Source:** the RFC section, or a decision of this design.

What breaking a rule leads to depends on the layer:

| Layer | When a rule is broken |
|---|---|
| parse, schema, validator | A broken `MUST` is reported as an **error** and makes the file invalid (a checker reports a record's as a reason of `INVALID_RECORD`); a broken `SHOULD` is reported as a **warning**, and the file stays valid |
| check | Nothing fails. The code is reported and **the result gets a status**, given in the check table's extra column, *Status when broken* |
| runner | The runner doesn't conform. Where a rule says the runner refuses, it reports the code |

The check layer is the only one laid out differently, with that extra
column, because breaking one of its rules changes what a result is. A parse,
schema or validator rule decides whether a file is valid, and only through
its `MUST`s.

A `MAY` row states what a tool may do. Leaving it out breaks nothing and
makes no tool non-conforming. The code is what a tool that does it reports.
Only the runner table, whose rules are about a tool's own actions, can have
`MAY` rows.

A tool reports every rule broken, except where another broken rule leaves what
a rule is about undetermined: spec §9's *What is checked* lists those cases,
closed (§11 item 28).

Codes reuse astra-tools' names (on its `main`) where the meaning hasn't
changed: `EXCLUDED_OPTION_SELECTED`, `INACTIVE_DECISION`,
`INCOMPATIBLE_OPTIONS`, `INVALID_INSIGHT_REF`, `MISSING_DECISION`,
`MISSING_REQUIRED_OPTION`, `OUTPUT_CYCLE`, `UNDECLARED_TEMPLATE_REF` and
`UNKNOWN_OPTION`. Its per-field reference codes (`INVALID_OUTPUT_INPUT`,
`INVALID_WHEN_REF`, …) merge into `UNRESOLVED_ADDRESS`, and
`DUPLICATE_INPUT`/`DUPLICATE_OUTPUT` into `DUPLICATE_KEY`. The specification's
catalogue (§8, section 9) is this list in final form.

### check

Read this table like the others: **the Rule column says what must hold**.
The extra column, **Status when broken**, is what the result gets when the
rule doesn't hold. A result for which every rule holds is `unchanged` and
`present`.

**Statuses.** A checker gives every planned result two statuses, one for its
record (`unchanged`, `stale` or `missing`) and one for its bytes (`present`
or `absent`). Evidence citing a result gets that result's first status.

| Status | Means |
|---|---|
| `unchanged` | The result has a valid record where its address says, and `STALE_RESULT` holds |
| `stale` | The result has a valid record where its address says, and `STALE_RESULT` doesn't hold. The checker says what changed |
| `missing` | The result has no valid record where its address says: `MISSING_RECORD`, `INVALID_RECORD` (including a record that breaks a parse or schema rule), `MISPLACED_RECORD` or `MISSING_RECORD_INPUTS` doesn't hold |
| `present` | The bytes at the result's default place hash to the record's `content_hash` and have its `size` |
| `absent` | Anything else is at the default place, nothing, a stand-in or other bytes included |

**Rules.**

| Code | Level | Rule | Status when broken | Source |
|---|---|---|---|---|
| `MISSING_RECORD` | MUST | Every planned result has a record at `.astra/records/{universe}/{name}.json` (or `{name}.json` for an output built once) in the analysis it belongs to | `missing` | 0005 §1 |
| `INVALID_RECORD` | MUST | The record at each planned result's place breaks no parse rule, and no schema rule against the record schema of its `spec_version`, or against the open variant when that version is newer than the checker's | `missing` | 0005 §2, tidy-up, D10 |
| `MISPLACED_RECORD` | MUST | The record at each planned result's place names that result in its `address` | `missing` | 0005 §1 |
| `MISSING_RECORD_INPUTS` | MUST | The record at each planned result's place has exactly one `inputs` item for each entry its output lists at the commit the record names, matched by `entry`, and no other item (their order carries no meaning) | `missing` | 0005 §2 |
| `STALE_RESULT` | MUST | Since the commit in a result's record, nothing has changed in its output's declaration (command, inputs and their order, decisions, format), its decisions' options, the content of its inputs, never what stands in for it, or the results it reads | `stale` | 0005 §4 |
| `ABSENT_RESULT` | SHOULD | Every result's recorded bytes are at its default place | `absent` | 0005 §1 |
| `STALE_EVIDENCE` | MUST | Every evidence citing a result cites an unchanged one | the cited result's status | 0005 §5 |

The results of an analysis from a commit that are read or cited are checked
by the same rules, through their records at the declared commit (0007
§4–5).

## 8. The specification

`docs/specification.md` is replaced by the normative text. The explainer it
holds today stays in git history for the docs project.

- **Keywords:** RFC 2119/8174, normative only in capitals.
- **Notation:** ABNF (RFC 5234).
- **Fields:** linked to the generated reference, never restated.

Sections:

1. **Conventions:** keywords, terms, notation, `spec_version`. What one version
   promises another is left to the versioning policy.
2. **Overview:** what ASTRA records, the two documents, and the four
   conforming roles: document, validator, checker, runner.
3. **Files:** `astra.yaml` is YAML 1.2 and invalid with duplicate keys.
   Records are JSON. Locations: `astra.yaml`, `.astra/records/…`,
   `results/…`.
4. **Names and grammars:** §4's ABNF, and how an address resolves through
   declarations.
5. **The analysis:** inputs, outputs (`type`, `format`, placeholders),
   decisions and options (constraints, `excluded`), conditional elements
   (`when` as on `main`), insights and evidence.
6. **Universes:** declaration, `derived_from`, the effective selection, and an
   output built per universe or built once.
7. **Composition:** declarations, the analysis stack, driving and consuming,
   pins across analyses, analyses from a commit.
8. **Results and records:** where results belong, where records and bytes go,
   what a record holds, and the statuses.
9. **Conformance:** §7's catalogue, one table per layer. The only place a rule
   is stated as a rule. Earlier sections link to it.
10. **Schema artefacts:** the files, their `w3id.org/astra` URIs, and which one
    is the contract.

## 9. Testing (this phase: the schema layer)

- **`rules.json`:** the harness checks each invalid fixture's error through
  `rules.json` (its absolute keyword location maps to the fixture's `# rule:`
  code), so the tests read what the tools read (D13).
- **Fixtures:** `tests/data/{valid,invalid}/<Root>-<nnn>-<what>.<ext>`, where
  `<Root>` is `Analysis` (an `astra.yaml`, `.yaml`) or `ProvenanceRecord` (a
  record, `.json`). Each is a whole document. Each invalid fixture is a
  minimal valid document with one thing broken, and starts with
  `# rule: <CODE>`, the rule it breaks. A record can't hold a comment, so its
  header lines are in a sidecar, `<Root>-<nnn>-<what>.header`.
- **One validation path:** every fixture is validated by a plain `jsonschema`
  2019-09 validator against the committed generated schema, as a consumer
  would. No LinkML is involved.
- **Failing for the right reason** (Ruling R24): an invalid fixture starts with
  `# rule:` and `# fails at: <JSON Pointer>`. The test asserts that the errors
  are reported there and nowhere else, that `rules.json` gives them the rule,
  and that the rule is a parse/schema code; a parse fixture's loader error
  gives exactly its code (a repeated key `DUPLICATE_KEY`, any other
  `INVALID_SYNTAX`). A second error is allowed only where the fixture declares
  it, in a third line `# also: <CODE> at <JSON Pointer>`: the errors there must
  be reported, and `rules.json` must give them that code.
- **Parse:** the harness loads YAML as YAML 1.2 under the core schema only
  (Ruling R19): `no`/`yes`/`on` stay strings, timestamps stay strings, `<<` is
  an ordinary key, `1_000` is a string, no `!!set`/`!!binary`/`!!omap`, a
  `%YAML` directive other than 1.2 is an error, duplicate keys raise (PyYAML is
  YAML 1.1 and keeps the last duplicate silently; ruamel's stock safe loader
  still resolves timestamps and merge keys), and a fixture with a duplicate
  key fails at parse (`# fails at: parse`). That fixture is excluded from the
  repository's own YAML linters (`yamllint`, pre-commit's `check-yaml`). A
  value with no JSON form raises too: a number that isn't finite or is beyond
  a double's range, and a string holding a lone surrogate (an escaped
  surrogate pair is one character). An entry whose key isn't a string is left
  out and its key reported (`load_document`): the invalid-fixture test counts
  it as `INVALID_ID` at its map, not through `rules.json`, and `load_yaml`
  raises on it, so no valid document has one. The harness reads a file's
  bytes as strict UTF-8 (a byte order mark may start it), and reads YAML
  1.2.2's characters, tabs and line breaks where ruamel.yaml departs from
  them: a tab separates wherever YAML allows white space outside indentation,
  and is refused in indentation; NEL, LS and PS are ordinary characters; a
  quoted scalar takes any character but a C0 control, and a plain scalar, a
  block scalar or a comment refuses DEL, the C1 controls but NEL, U+FEFF,
  U+FFFE and U+FFFF. It is checked against yaml-test-suite: its error cases
  each raise, and its well-formed cases that hold a tab, vendored with their
  `in.json`, each load to it. A fixture that the linters' loaders refuse (a
  tab, a C1 control, bytes that aren't UTF-8) is excluded from them too.
- **Records:** the harness reads a record as spec §3 does (`load_json`):
  strict UTF-8 with no byte order mark, then `json.loads` with hooks that
  refuse a repeated name (`DUPLICATE_KEY`), `NaN` and `Infinity`, and a
  number beyond a double's range, and a walk that refuses a lone surrogate
  (`INVALID_SYNTAX`). Record parse fixtures cover each, and a comment, a
  trailing comma, a byte that isn't UTF-8 and YAML's block form. The
  specification's JSON examples are read the same way.
- **The extension:**
  - fixtures for a bad map key, the string shorthand and a null value
  - a structural test that walks the generated schema and asserts that every
    id-keyed map has `propertyNames` and its one value form
- **Drift:** regenerate into a temporary directory and compare with what's
  committed.
- **Ajv:** `just check-ajv` compiles the three committed JSON Schemas under
  `strict: true`, with the Ajv pinned in `tools/ajv/`. CI runs it.
- **Lint:** `linkml-lint` is clean.
- **Examples:** every `astra.yaml` under `examples/` validates.
- **The open variant:** a record with an unknown field fails the closed schema
  and passes the open one.

## 11. For the tidy-up RFC

Changes this design makes beyond the accepted RFCs. They belong in the tidy-up
RFC as further numbered changes:

1. Element ids are LinkML `key`s, not `identifier`s (D4).
2. One id grammar, defined once; universe ids lose `-` (D5).
3. The reserved-word list goes; ids that one field could resolve to must be
   distinct (today, inputs and outputs) (D5).
4. `Analysis.id` is removed (D6).
5. Everything referenced by id is a map: `inputs`, `outputs`, `universes` and
   `analyses` become maps (D2).
6. Map keys follow the id grammar; map entries take one form: objects, except
   the compact `Universe.decisions` (D3).
7. `Evidence.id` is removed.
8. `Insight.notes` becomes `description`.
9. `Evidence.version` only with `doi`.
10. `ProvenanceRecord.version` becomes `spec_version` (D10).
11. Optional fields don't take `null` (D12).
    A record with a field its version doesn't define is invalid to a checker of
    that version (D10); RFC 0005 §2 can be read as always ignoring unknown
    fields, so this reading needs stating. And no list of strings holds the
    same entry twice (`DUPLICATE_ENTRY`).
12. A declaration's `url` is a remote URL (`scheme://…` or scp-like
    `[user@]host:path`), with no ASCII space (`%20`, item 21); anything local
    is a `path`.
13. Already pending in the draft: the FragmentSelector swap and
    `Analysis.version` → `spec_version`. The swap, the draft's change 4
    (*`FragmentSelector.page` is removed and `conforms_to` names the
    syntax*), also gives a location an optional `conforms_to`, the IRI of its
    fragment syntax (a PDF fragment without it), and `value` a pattern: a
    fragment identifier's characters, `%` only before two hex digits.
14. Commit ids and content hashes are lowercase hexadecimal, as git and Git LFS
    pointers write them (RFC 0007 and RFC 0005 don't say which case).
15. Paths are `/`-separated, with no backslash and no ASCII control character;
    an input's path doesn't end in `/` (RFC 0004 and RFC 0006 say only that they
    are relative).
16. A record's times have each field in its range (no leap second) and are
    `xsd:dateTime` in RDF (RFC 0005 gives only the written form).

17. Every rule has a code in one catalogue (the specification's §9) (D9).
18. A result's bytes are `present` or `absent`, and tools may report more:
    `modified` is not a status. RFC 0005 §1's MUST on what a result's default
    place holds is broken as `absent` (`ABSENT_RESULT`).
19. `spec_version`, in an analysis and in a record, has three parts,
    `MAJOR.MINOR.PATCH`, without leading zeros, such as `0.1.0` (`main` also
    took two parts and leading zeros, such as `1.0` and `01.1.0`, and RFC 0005
    gives only the example `0.1.0`).
20. `Evidence.doi` is a DOI name (ISO 26324) in the `10` directory: `10.`, a
    registrant code of digit runs joined by `.`, `/`, and a suffix with no
    control character (C0, DEL or C1) and no ASCII space at either end. It
    accepts every ISBN-A (`10.978.8889637/173`), which `main`'s
    `^10\.\d{4,}/.*$` rejected, and spaces inside the suffix
    (`10.3929/ethz-a- 007549606`). Where `main` took any suffix, it rejects an
    empty one, a control character and an ASCII space at either end. It also
    rejects two forms ISO 26324:2022 allows: a shortDOI (`10/aabbe`), which
    doi.org resolves, and any other directory indicator (`11.1/x`), which no
    resolver serves. A shortDOI is an alias for a full DOI, and tools compare
    DOIs as strings, so a work is cited by its full DOI, under one name.
21. What the character classes admit above U+007F (spec §4, and the table
    in §4 here). `Option.excluded` and `AnalysisDeclaration.url` take
    `[^\x00-\x20\x7f]`, which admits non-ASCII spaces, format characters,
    U+2028/U+2029 and the C1 controls, so a reason made only of them is not
    blank (the draft's change 14, *`excluded` holds the reason*, gives this
    range). The suffix of an `Evidence.doi` takes `[^\x00-\x20\x7f-\x9f]` at
    either end and `[^\x00-\x1f\x7f-\x9f]` inside, which admit format
    characters, U+2028/U+2029, private use and noncharacters: ISO 26324
    excludes them, and no rule checks them. A `url` holds no ASCII space or
    control character, though git fetches a remote with a space (RFC 0007 and
    the draft's change 28, *A `url` is a remote's URL*, don't say which
    characters a `url` holds): a space is written `%20` in a `scheme://` URL,
    which git decodes, and since git doesn't decode the scp-like form,
    `[user@]host:my dir/x` is rewritten `ssh://[user@]host/~/my%20dir/x`.
22. `PIN_LIKE_COMMENT` is removed. RFC 0003 recommends a warning on an input
    whose line comment looks like a pin (`- f1_score #svm`), and nothing says
    what looks like one; a validator reads a file's data, not its comments.
    Spec §4 keeps the stray space as advice to authors: a pin is written with
    no space before its `#`.
23. A value with no JSON form makes a file invalid. A key that isn't a string
    is `INVALID_ID` at its map, and its entry is left out. A non-finite
    number, one beyond a double's range, and a lone surrogate are
    `INVALID_SYNTAX`. This states the draft's change 36 (*Files are YAML
    1.2*), "a file means the same as the JSON it converts to", and needs no
    text of its own.
24. A record is strict JSON, judged as a document: RFC 8259 JSON text in
    UTF-8 with no byte order mark, using only JSON's forms (no comment,
    trailing comma, `NaN` or `Infinity`), all `INVALID_SYNTAX`, with no name
    written twice in an object (`DUPLICATE_KEY`, which `json.loads` and
    `JSON.parse` don't report), and its strings and numbers as item 23 has
    them. A record that breaks a parse or schema rule leaves its result
    `missing`: a checker reports `INVALID_RECORD`, with the parser's code, or
    the one `rules.json` gives the schema error, as its reason. RFC 0005 says
    only that records are `.json` files (its §1), judged in the check layer
    (its §2), and the draft's change 25 (*A record holds only its version's
    fields*) only that a field its version doesn't define makes a record
    `missing`.
25. An `astra.yaml` is UTF-8, and may start with a byte order mark but holds
    none anywhere else outside a quoted scalar (YAML 1.2.2 §5.2 also allows
    UTF-16 and UTF-32, and a byte order mark at the start of each document;
    the draft's change 36, *Files are YAML 1.2*, names no encoding).
    Otherwise its characters, tabs and line breaks are YAML 1.2.2's, which
    spec §3 states without changing a verdict. Migration: re-save a UTF-16 or
    Latin-1 file as UTF-8, and delete a byte order mark that doesn't start
    the file and isn't in a quoted scalar.
26. A universe's own `decisions` give each decision one key, and no list holds
    two spellings of one entry (`DUPLICATE_ELEMENT`); RFC 0004:221 allows
    agreeing spellings. A derived universe can still set a decision it
    inherits under another spelling (spec §4, §6, §7).
27. Driving and pins are defined once (spec §6, §7, §8), where RFC 0004
    leaves each point open. A derived universe sets each of its own
    selections on the decision, so every inherited key for it takes the new
    option. A universe drives a declaration when a key in its effective
    selection goes through every declaration from its analysis's file to
    that one, and each chain of declarations, two that end in one
    declaration included, is driven by all of an analysis's universes or by
    none (`PARTIALLY_DRIVEN`). An analysis with no decisions and no
    universes of its own is driven by every universe that drives the chain
    before it, unless its declaration leads back to an analysis already on
    the chain, itself included, so RFC 0004's
    `subanalysis3.output3_per_universe` is built in the root's universes;
    one with universes of its own keeps them unless a key drives it. An
    unpinned read or a consumed decision in the file of the analysis whose
    universe is being built needs the address's chain driven, up to its last
    declaration (`UNDRIVEN_DECLARATION`). A pin resolves in the file it is
    written in, and names a universe of the first analysis along its
    reference, from that file's own, whose universes drive the reference's
    declarations from that analysis's file to its last, or else of the
    analysis whose output it is (`UNKNOWN_PIN_UNIVERSE`).
28. A rule isn't checked where another broken rule leaves what it is about
    undetermined. Spec §9's *What is checked* lists the cases, closed. Every
    case starts from a broken `MUST`, so it changes which codes are reported,
    never validity.
29. Git is read one way (spec §3, *Reading git*): the work tree without
    `.git`; symlinks never followed, so a symlink is an input's file only as
    a stand-in the validator recognises and never a declared analysis;
    gitlinks crossed at a commit, never for tracking; the innermost
    repository; the index for tracked, so a staged input passes and one in a
    plain data submodule fails `INPUT_NOT_TRACKED`; HEAD or MERGE_HEAD for
    the working tree's commit (`COMMIT_NOT_ANCESTOR`); a submodule's URL from
    `.gitmodules` at the commit; blobs unfiltered, so an `astra.yaml` at a
    commit is parsed from its blob. RFCs 0004, 0006 and 0007 leave all of it
    open.
30. Getting a commit from a remote is checked each time, a kept copy counts
    as got, and a commit that can't be got is reported on the outermost
    declaration in a file outside every analysis from a commit (spec §7,
    *Validity*; `REMOTE_UNREACHABLE`). RFC 0007 §6 says the answer can't
    change: the rest of it can't, and a validator can still remember it.

The first seventeen are in the tidy-up RFC draft as its changes 4 and 12–28;
item 18 is not yet. Item 22 is the draft's change 8, *The warning on a comment
that looks like a pin is removed*, item 26 its change 33, *One spelling of
each entry*, and item 27 its change 32, *Driving and pins are defined once*.
`rules.json` (D13) is not: it is a published artefact of the implementation,
like the generated JSON Schemas, and the RFC covers only the specification and
the schema. Items 19, 20 and 21, item 12's no-space clause and item 14's
content hashes are in the specification and the schema only (Tom,
2026-11-04), and items 23, 24, 25, 28 and 30 are in the specification only.
Item 29 is in the specification and the schema only, except that a path
crosses a gitlink at a commit, where the submodule's commit is got from, and
what failing to get it reports: that is the draft's change 35, *A
submodule's commit is got like a remote's*.

    with a `url` whose remote lacks its `commit`, each read through by an
    output's `inputs`: only `COMMIT_NOT_FOUND` and `REMOTE_UNREACHABLE`, and
    no `COMMIT_NOT_ANCESTOR`, `MISSING_DECLARED_ANALYSIS` or
    `UNRESOLVED_ADDRESS`;
  - an analysis from a commit whose file selects an option its decision
    doesn't have: `DECLARED_ANALYSIS_INVALID` on the declaration and
    `UNKNOWN_OPTION` in the commit's file;
  - a selection key that names no decision: only `UNRESOLVED_ADDRESS`. An
    output whose `when` names an option its decision doesn't have: only
    `UNKNOWN_OPTION`, with no `INPUT_NOT_BUILT` for the outputs that read it;
  - a planned result with no record: only `MISSING_RECORD`.

  Its validator cases also read git as spec §3's *Reading git* has it (§11
  item 29):
  - the analysis `lib` as the submodule `vendor/lib` of the root's
    repository (the v0.1 review's F026): `lib`'s own
    `previous: {path: ., commit: LIBC1}` passes (L1). The root's
    `{path: vendor/lib, commit: LIBC2}`, a commit only the submodule has,
    gives `COMMIT_NOT_FOUND`, and `{path: vendor/lib, commit: ROOTC}`, which
    crosses the gitlink at the root's commit, passes (L2);
  - a staged input passes. An ignored input gives `INPUT_NOT_TRACKED`, and
    so does an input in a plain data submodule, at HEAD and at a commit;
  - a symlink at an input's path that the validator doesn't recognise as a
    stand-in gives `MISSING_INPUT_FILE`, and a declaration whose `path` is a
    symlinked folder `MISSING_DECLARED_ANALYSIS`;
  - during a merge, an uncommitted declaration of a commit that only
    MERGE_HEAD has as an ancestor gives no `COMMIT_NOT_ANCESTOR`;
  - in the working tree, a declaration of a submodule that isn't checked out
    gives `MISSING_DECLARED_ANALYSIS`;
  - a submodule crossed at a commit read from a remote, with a relative
    `.gitmodules` URL, passes. The same with the submodule's remote gone and
    nothing kept gives one `REMOTE_UNREACHABLE`, on the outer declaration;
  - an `astra.yaml` at a commit whose `.gitattributes` sets a filter or a
    `working-tree-encoding` is judged by its blob.

  Its validator cases also get commits from remotes as spec §7's *Validity*
  has it (§11 item 30). In the first three, the root declares `sub` by
  `path`, `sub` declares `upstream` by `url`, and `upstream` declares
  `nested` by `url`:
  - `nested`'s remote is gone, and a copy of its commit was kept from an
    earlier fetch: valid;
  - `nested`'s remote is gone, nothing was kept, and the answer for
    `upstream`'s commit is remembered: one `REMOTE_UNREACHABLE`, on `sub`'s
    declaration of `upstream`, and nothing else;
  - `upstream` declares a `path` and a `commit` that its remote has lost: the
    same;
  - the root declares `old: {path: lib, commit: C}`, and at `C` `lib` is a
    gitlink whose submodule's URL is gone: with nothing kept in
    `.git/modules`, one `REMOTE_UNREACHABLE`, on `old`; with the submodule
    kept there, valid.

## 13. Open points

- ~~**Agreeing spellings.**~~ **Settled:** two spellings of one decision in
  a universe's own `decisions`, agreeing or not, are an error, and so are two
  spellings of one entry in a list (`DUPLICATE_ELEMENT`, tidy-up change 33;
  §11 item 26). RFC 0004:221 allows agreeing spellings, and its open question
  (:688) asked only whether they should warn. A derived universe can still
  set a decision it inherits under another spelling.
- **`when` on an inactive decision.** What a condition naming a switched-off
  decision means is #93's question, out of scope. The specification states
  `main`'s semantics and says no more.
- ~~**An analysis with no decisions, reading a per-universe output.**~~
  **Settled:** an analysis with no decisions and no universes of its own is
  driven by every universe that drives the chain before it, and so by every
  universe of the driver when the driver's file declares it, unless its
  declaration leads back to an analysis already on the chain, itself
  included (tidy-up change 32; §11 item 27). So, as RFC 0004 §3–§4 has it,
  its output that reads one built per universe without a pin is built in the
  root's universes, and RFC 0005 §1 records it there as
  `subanalysis3.output3_per_universe`, while `output3` is still built once
  and belongs to `subanalysis3`. An analysis with universes of its own keeps
  them unless a key drives it. The bound keeps names finite: without it, such
  an analysis `x` that declares `self: {path: .}` would be driven as
  `x.self`, `x.self.self` and so on, each a name for its results.
- ~~**A driven analysis reading its driver's elements.**~~ **Settled:** the
  analysis whose universe is being built is always built in it, and
  `UNDRIVEN_DECLARATION` applies only in its file (RFC 0004:411), so an
  analysis it drives consumes its decisions and reads its outputs back
  through `..` (`iris.random_seed` in `examples/iris_pipeline`, RFC 0004:581,
  :651). An output built once is read without a pin through any declaration
  (RFC 0004:336, RFC 0007 §3).
- **One result, two names.** RFC 0004 lets one analysis be reached through
  two driven declarations (`stage.inner` and `inner`), and RFC 0005 §1 names a
  result by its chain of declarations, so one result has two record paths
  (`.astra/records/u1/stage.inner.d.json`, `…/inner.d.json`). For the check and
  runner phase to settle (probably: the name through the fewest declarations,
  then the first in key order). Only driven declarations name a result (spec
  §8): a pin through an undriven declaration names a universe of an analysis
  further along its reference (tidy-up change 32), and the root is never
  driven (spec §7). So the point is about two driven declarations, never an
  undriven one or a back-edge to the root (`iris: {path: ..}` in
  `examples/iris_pipeline`).
- **What the `iri` pattern leaves out** (`Environment.iri`,
  `FragmentSelector.conforms_to`). It checks an IRI's scheme, its characters
  (RFC 3987's, without the bidi controls RFC 3987 §4.1 forbids) and its
  percent-encoding, not its structure. So it accepts strings
  RFC 3987 rejects, such as `urn:x:a[b` and `http://h:x:y/` (authority, port
  and IP literal unchecked), and, anywhere, every non-ASCII character outside
  RFC 3987's `ucschar` other than the C1 controls: noncharacters, the specials
  U+FFF0–U+FFFD, the tag characters and variation selectors of
  U+E0000–U+E0FFF, and private-use characters (RFC 3987 allows private use
  only in a query, which a character class can't place). It rejects the IRIs
  with nothing after the scheme's `:`, such as `x:` and `x:#y`. RFC 3987's
  full grammar as the pattern would close the gap, at the cost of a long
  pattern in the regex subset Python and ECMA-262 share; Tom chose the
  characters (2026-11-04). The tidy-up RFC is to record the narrowing, so that
  the pattern is the whole rule.
- ~~`requires-python`~~ **Settled:** `>=3.10`, the first version whose
  `importlib.resources` reads namespace packages (tested while planning).
