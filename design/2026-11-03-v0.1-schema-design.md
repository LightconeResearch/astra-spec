# v0.1 schema: design

- **Date:** 2026-11-03
- **Branch:** `v0.1-schema`, from `main` at `1bc6eb8`
- **Status:** implemented on `v0.1-schema`

## 1. Goal and scope

**Goal.** One schema, one contract and one specification for ASTRA v0.1 that
implement RFCs 0003–0007 and the draft RFC *Settling the schema for v0.1*
exactly, with every rule enforced as high up as it can be.

**In scope**

- the LinkML schema (`src/astra/schema/`)
- the generated JSON Schema, which is the contract (§3)
- the normative `docs/specification.md`
- the schema-layer tests (§9)
- `examples/iris` and `examples/iris_pipeline`, migrated (they double as valid
  fixtures)
- RFCs 0003–0007 and the draft *Settling the schema for v0.1* (the tidy-up
  draft), whose changes 4 and 11 were pending at the start of this work

**Out of scope**

- `when` (#93): `when` keeps the meaning it has on `main`
- citing insights: `Option.insights` keeps its meaning
- recipes: `Recipe`, `Resources` and both `container`s are untouched
- every other docs page (`index.md`, `getting-started.md`, `cli.md`,
  `llms.txt`, `README.md`). They will be stale on this branch, and a failing
  docs build is expected for this phase
- tooling (astra-tools, typescript-astra) and the validator, check and runner
  conformance suite (§12)

**Done means**

- the schema implements every statement of the in-scope RFCs, shown by the
  traceability checklist (§10)
- every rule sits in the highest layer that can enforce it (§7)
- every valid and invalid fixture passes or fails through the published JSON
  Schema, failing where it says it fails
- the specification is enough to build a validator, checker or runner from
  without reading the RFCs

**Approach.** A clean rewrite against the traceability checklist, not one RFC
at a time: later RFCs undo earlier forms (0004 replaces 0003's
`Universe.analyses`, 0006 replaces 0004's inputs, tidy-up flips lists to
maps), so each rule is written once, in its final form.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The generated JSON Schema is the contract. LinkML is the source we edit | Language-neutral (astra-tools, typescript-astra, editors through `yaml-language-server`) and published at `w3id.org/astra`. It is what LinkML's own `linkml-validate` uses by default ([Validating data](https://linkml.io/linkml/data/validating-data.html)), and it has the highest feature coverage of LinkML's generators on the project's [dashboard](https://linkml.io/linkml/generators/dashboard.html): 62% of 66 feature tests fully implemented, against 47% for Pydantic, including the precondition rules, `value_presence`, `exactly_one_of` and dict inlining this design depends on. Its weaker rows (`unique_keys`, keys, the regex dialect) are where D3's extension and the fixtures compensate. LinkML has no official tiering of generators ([governance](https://linkml.io/linkml/maintainers/generator-governance.html)) |
| D2 | Everything referenced by id is a map keyed by id. A list is used only for what is a list (`evidence`, a record's `inputs`, and lists of strings) | One principle. Uniqueness is structural (duplicate keys are invalid YAML 1.2), and the id is written once. Order carries no meaning in any keyed collection |
| D3 | A small extension of LinkML's JSON Schema generator adds `propertyNames` to every id-keyed map and allows one written form per map entry | Stock LinkML 1.12.1 checks neither map keys nor the form of map values (probe, §3) |
| D4 | Element ids are LinkML `key`s, not `identifier`s. The only `identifier` is `Environment.iri` | A key is unique within its container, which is what author-given ids are. An identifier is globally unique, which only things named by the world are. As RDF, `identifier`s merged unrelated elements (`astra:none`) |
| D5 | One id grammar, `[a-z][a-z0-9_]*`, everywhere. The reserved-word list goes. Ids that one field could resolve to are distinct | After RFC 0004, an address's kind comes from the field it's written in, so category words can't shadow anything. The one real ambiguity is two kinds one field takes (today an input and an output, through `Output.inputs`). JSON Schema can't relate the keys of two maps, so it is a validator rule (`AMBIGUOUS_ID`), worded generally so that it covers any field that later takes more than one kind. Merging `inputs` and `outputs` into one map was considered and rejected: it costs the inputs/outputs vocabulary to save one simple rule |
| D6 | `Analysis.id` is removed | Nothing references it: declarations name analyses locally, results go by address, and identity is commit plus path (RFC 0007) |
| D7 | The package ships only artefacts: the LinkML sources, the generated JSON Schemas and the record's JSON-LD context. No generated Python and no runtime dependency | Nothing in the package can disagree with the contract. The pydantic models enforce neither `rules` nor `propertyNames`, and needed their ids injected |
| D8 | Fields are defined in LinkML (descriptions are their normative text, and the field reference is generated). The specification carries concepts, grammars and the rule catalogue, and links to the reference | One statement of each fact, so the two can't drift |
| D9 | A normative rule catalogue: each rule has a code, a layer, a level (`MUST`/`SHOULD`/`MAY`), one statement of what holds and a source, all written one way (§7) | Machine-checkable later by a conformance suite (§12) |
| D10 | The record's `version` becomes `spec_version`. The record schema ships closed, plus a generated open variant for checkers reading records of a greater minor version than their own | The same name for the same concept. RFC 0005 wants both "only its version's fields" and "ignore unknown fields", which takes two schemas |
| D11 | A named type exists only if more than one field uses it. A pattern used once is written on its field | Keeps `types.yaml` to the grammars the format is built from |
| D12 | Optional fields don't accept `null` | One way to write a file |
| D13 | A machine-readable catalogue, `rules.json`, is derived, never written by hand: the rules (code, layer, level, statement, source, status) are extracted from the specification's §9, which stays the hand-written source; the error map (where in a JSON Schema an error comes from → its code) is derived from the schema, where each constraint names the rule it enforces | The specification-body practice (CommonMark extracts its tests from its spec; the W3C's webref extracts IDL and CSS from specs; a malformed extract is a spec bug). Every tool then maps errors to the same codes and shows the same wording, and the tests read the same file as the tools |

## 3. Architecture and artefacts

### Sources (`src/astra/schema/`, hand-written)

| Module | Holds | Imports |
|---|---|---|
| `types.yaml` | The named types of §4, with the grammar pieces in `settings` so the `structured_pattern`s are built from them | `linkml:types` |
| `analysis.yaml` | Root of `astra.yaml` (`tree_root: Analysis`): Analysis, AnalysisDeclaration, Input, Output, Recipe, Resources, Decision, Option, Universe, DecisionSelection, OutputType | `types`, `insight` |
| `insight.yaml` | Insight, Evidence, TextQuoteSelector, FragmentSelector | `types` |
| `provenance.yaml` | Root of a record (`tree_root: ProvenanceRecord`): ProvenanceRecord, Generation, RecordedInput, Environment, Runner, with PROV-O mappings | `types` |

`universe.yaml` folds into `analysis.yaml`. It was separate only because
universes lived in files of their own.

### Generated (`src/astra/schema/generated/`, committed)

| File | Root | Generator options | `$id` |
|---|---|---|---|
| `analysis.schema.json` | Analysis | closed, `--no-include-null` | `https://w3id.org/astra/0.1/analysis.schema.json` |
| `provenance.schema.json` | ProvenanceRecord | closed, `--no-include-null` | `https://w3id.org/astra/0.1/provenance.schema.json` |
| `provenance.open.schema.json` | ProvenanceRecord | `--not-closed`, `--no-include-null` | `https://w3id.org/astra/0.1/provenance.open.schema.json` |
| `provenance.context.jsonld` | | LinkML's context, post-processed by `tools/jsonld_context.py` |
| `rules.json` | | `tools/rules.py` (D13) |

- **Built by** `just gen-schema`, which runs the extension (below) for the
  three JSON Schemas and `tools/jsonld_context.py` for the record's context.
- **Committed** so that every change to the contract is a diff in review and
  building the package needs no LinkML. A test regenerates them and fails on
  any difference.
- **Versioned at release.** Sources keep the placeholder `version: 0.0.0`, and
  `just release` regenerates the artefacts with the release version, then
  commits them regenerated as `dev` after the tag. A build stamps the tag at
  HEAD, or `dev` where it finds none: between releases, or where the tags
  weren't fetched. The version's series goes in each `$id`: `X.Y` for a
  release `X.Y.Z`, a pre-release's whole version (`0.1.0rc1`), or `dev`. A
  patch release never changes what is valid, so `just release` compares a
  patch's regenerated schemas and error map with its minor version's greatest
  release (`tools/check_patch.py`).
- **The field reference** (`docs/elements/`) comes from `gen-doc`, run over
  both roots (`analysis.yaml` and `provenance.yaml`), as part of the docs build.
- **Each JSON Schema's `$id`** is the URI of its own file under its minor
  version (table above), so the closed and open record schemas are distinct
  resources, and so are two minor versions held side by side. The patches of
  one minor version share it (spec §1, §10).
- **Only standard keywords at the top level:** LinkML's `metamodel_version` is
  dropped and the schema version moves into `$comment`, so strict validators
  (Ajv) compile the contract.
- **`rules.json`** (D13) holds `rules`, one entry per catalogue code (`code`,
  `layer`, `level`, `statement` as the cell's inline Markdown with links
  reduced to their text, `source`, and `status` for the check layer), and
  `errors`, a map from a JSON Schema error's absolute keyword location (the
  schema's `$id`, `#`, and a JSON Pointer to the failing keyword, e.g.
  `https://w3id.org/astra/0.1/analysis.schema.json#/$defs/AnalysisDeclaration/properties/commit/pattern`)
  to its code. The rules are parsed from §9 with a Markdown parser, never by
  regular expressions, and extraction is strict: a malformed row, a duplicate
  code, an unknown layer or level, or a statement whose keyword contradicts
  its level fails the build. Each constraint in the LinkML sources names its
  code (an annotation on the type, slot or class rule); only keywords whose
  code never varies take a default: `required` outside a rule;
  `additionalProperties`; `type` (`WRONG_TYPE`), except on a map key, which
  takes the key's code; `minProperties`/`minItems` of 1 (`EMPTY_COLLECTION`);
  `uniqueItems`; `enum`; `minimum`. Every constraint in the generated schemas
  has a code, and every code the schema names is a parse/schema code of §9.
  Fixtures are not listed in `rules.json` (they aren't shipped); a test links
  them to the catalogue.
- **No JSON-LD context for `astra.yaml`** (Ruling R18). LinkML's flat context
  gives a wrong RDF reading of id-keyed maps (an entry's key becomes a
  predicate) and merges terms that share a name (`decisions`). A faithful
  context (`@container: @id`, scoped contexts) is later work. The record's
  context maps its terms onto PROV-O. A record's RDF is what JSON-LD 1.1's
  toRdf gives with it, plus each node's class URI as its `rdf:type` (spec
  §10), not LinkML's RDF conversion, which reads any value without `://` as
  a CURIE and fails on a `urn:` IRI.
- **The record's context is prefix-free.** Stock `gen-jsonld-context`
  declares `astra`, `linkml`, `prov`, `schema` and `xsd` as simple terms
  ending in `/` or `#`, which JSON-LD 1.1 makes prefixes, so an environment
  `iri` such as `prov:env:1` would become `http://www.w3.org/ns/prov#env:1`.
  `tools/jsonld_context.py` takes LinkML's context, drops those terms after
  writing every `@id` and `@type` as a full IRI, and adds `"@version": 1.1`,
  so that a JSON-LD 1.0 processor, which reads any term as a prefix, rejects
  it. No term is a prefix, so every `iri` is read exactly as written.

### The generator extension

- **What it is:** one dev-only module, `tools/jsonschema_generator.py`,
  subclassing LinkML's `JsonSchemaGenerator`. Everything else is stock LinkML,
  pinned at `linkml==1.12.1` as a dev dependency.
- **What it does,** for every multivalued slot inlined as a dict:
  1. adds `propertyNames` with the key slot's type (its `pattern`)
  2. allows one written form per entry:
     - **object form only** (`seed_42: {}`): removes LinkML's string and null
       alternatives, and removes the key slot from the entry's object, so the
       id is written once, as the key (`seed_42: {id: seed_42}` fails)
     - **compact form only** when the class has its key and exactly one other
       slot: the value is that slot's type. In this schema that's only
       `DecisionSelection`, so `Universe.decisions` is `model: svm`
  3. emits `uniqueItems: true` on every multivalued slot of scalars (lists of
     strings), so no list holds the same entry twice
  4. drops `$defs` the root can't reach, and the non-standard top-level
     keywords (above)
- **And for every class-level check** (an `exactly_one_of`, a class rule):
  5. moves it into its own member of `allOf` (the `exactly_one_of` first, then
     the rules), guarded by the types of what it reads:
     `{if: G, then: {oneOf: […]}}`, and `{if: G + the rule's if, then: the
     rule's then}`, where `G` is `{type: object, properties: {f: {type: <f's
     JSON type>}}}` over the fields `f` the check reads. A check is skipped
     only where a `type` keyword already fails, so no verdict changes, and a
     value of the wrong type is `WRONG_TYPE` alone. Each `required` in a check
     gets its fields in a `properties` beside it, inside a `not` too, so that
     Ajv compiles the schema under `strict: true` (`just check-ajv`, in CI)
- **Why it's needed** (a probe with LinkML 1.12.1, on `main`'s schema and a
  scratch schema):
  - map keys aren't checked at all: a decision `Not-A-Valid-Id!` passes
  - map values also take `"label"` and `null`
  - a class-level check only tests whether a key is there: a declaration
    written as a string, or `url: null` beside `path`, also gets
    `INVALID_DECLARATION_SOURCE` or `URL_WITHOUT_COMMIT` beside its
    `WRONG_TYPE`; and LinkML writes a field that must be absent with its
    `properties` beside the `not`, which Ajv's `strictRequired` rejects
  - `main`'s published JSON Schema rejects `main`'s own valid fixture and
    `examples/iris`: the rule `label_and_options_required_when_not_aliased`
    turns `options` into an array check. The tests missed it because valid
    fixtures went through the dataclasses, not the JSON Schema
- **Upstream.** Both behaviours are general, so the module is written to be
  offered to LinkML as a whole.

### Package

- **The wheel** holds `astra/schema/`, the sources and `generated/`, as the
  namespace package `astra.schema`, found through `importlib.resources`.
  `requires-python` is the lowest version where that works for namespace
  packages: **3.10** (tested: 3.9 fails, 3.10 and 3.11 work).
- **Dependencies:** none.

### Removed

- `src/astra/datamodel/` (the dataclasses and the pydantic models)
- `src/astra/schema/universe.yaml`
- the `gen-python`, `gen-project` (Python) and `_fix-python-keywords` recipes
- the `from:` → `from_:` rewrite in `tests/test_data.py`
- the `linkml-runtime` dependency

## 4. Names and grammars

### Grammar (for the specification, ABNF per RFC 5234)

```abnf
id               = lower *( lower / DIGIT / "_" )
lower            = %x61-7A                      ; a-z
address          = id *( "." id )               ; [declaration "."]... element
reference        = address [ "#" id ]           ; "#" pins a universe
option-reference = address "." id              ; a decision's address, then an option id
condition        = [ "~" ] option-reference     ; "~": the option is not selected
```

The last segment of an `option-reference` is always the option, so a decision
of a declared analysis is `iris.random_seed.seed_42`.

### Named types (`types.yaml`)

| Type | Pattern | Used by |
|---|---|---|
| `id` | `^[a-z][a-z0-9_]*$` | every map key but those of `Universe.decisions`; also `Universe.derived_from`, `Option.insights` and the values of `Universe.decisions` |
| `address` | `id` joined by `.` | `Output.decisions`, the keys of `Universe.decisions` |
| `reference` | `address`, optionally `#` `id` | `Output.inputs`, `Evidence.artifact`, `ProvenanceRecord.address`, `RecordedInput.entry` |
| `option_reference` | `address` `.` `id` | `Option.requires`, `Option.incompatible_with` |
| `condition` | optional `~`, then `option_reference` | `Output.when`, `Decision.when` |
| `commit_id` | `^([0-9a-f]{40}\|[0-9a-f]{64})$` | `AnalysisDeclaration.commit`, `Generation.commit` |
| `content_hash` | `^sha256:[0-9a-f]{64}$` | `ProvenanceRecord.content_hash`, `RecordedInput.content_hash` |
| `spec_version` | `MAJOR.MINOR.PATCH`, no leading zeros | `Analysis.spec_version`, `ProvenanceRecord.spec_version` |
| `timestamp` | `YYYY-MM-DDThh:mm:ss.sssZ`, each field in its range (month 01–12, day 01–31, hour 00–23, minute and second 00–59); RDF datatype `xsd:dateTime` | `Generation.started`, `Generation.finished` |
| `iri` | an IRI (RFC 3987): a scheme, `:`, then RFC 3987's characters, `%` only before two hex digits and at most one `#`, `^[A-Za-z][A-Za-z0-9+.-]*:(C\|%[0-9A-Fa-f]{2})+(#(C\|%[0-9A-Fa-f]{2})*)?$` with C `` [^\x00-\x20\x7f-\x9f<>"{}\|\\^`%#\u200e\u200f\u202a-\u202e] `` (no ASCII space, ASCII control or C1 control, and none of the bidi formatting characters RFC 3987 §4.1 forbids: U+200E, U+200F, U+202A–U+202E). `typeof: string`, never `uri`, whose `format: uri` Ajv strict rejects; the structure is unchecked (§11 item 38) | `Environment.iri`, `FragmentSelector.conforms_to` |

`id`, `address`, `reference`, `option_reference` and `condition` are
`structured_pattern`s built from one `id` setting, so the id grammar is
written once.

**Every `$` outside a lookahead is written `$(?!\n)`, every anchored pattern
ends in one, and no pattern uses `.`, `\s`, `\S`, `\d`, `\w` or `\b`.**
Python's `re`, which Python JSON Schema validators use, lets `$` match
before a final newline, and ECMA-262's `$` doesn't. Without the lookahead
`"a\n"` (a YAML block scalar gives one) would be a valid `id` in Python and
invalid in JavaScript. The
shorthand classes differ in the same way (Python's `.` matches `\r`, its `\s`
includes `\x1c`–`\x1f`), so patterns use explicit classes: `[0-9]`,
`[^\x00-\x20\x7f]` for a character other than an ASCII space or control,
`[^\x00-\x1f\x7f]` for any character but an ASCII control, and
`[^\x00-\x20\x7f-\x9f]` and `[^\x00-\x1f\x7f-\x9f]` for the same two
without the C1 controls (U+0080–U+009F). The patterns below are written in
the short form, for readability.

Above U+007F a class leaves out only what it names, so six fields admit
characters that aren't visible (spec §4; §11 item 21):

| Field | Class | Admits above U+007F |
|---|---|---|
| `Option.excluded`, `AnalysisDeclaration.url` | `[^\x00-\x20\x7f]` | every character: non-ASCII spaces (U+00A0, U+3000), format characters (U+200B, U+FEFF, U+202E), U+2028/U+2029 and the C1 controls |
| `FragmentSelector.value` | ``[^\x00-\x20\x7f"#%<>\[\\\]^`{\|}]``, or `%` and two hex digits | every character, as for `Option.excluded` |
| `Evidence.doi`, its suffix | `[^\x00-\x20\x7f-\x9f]` at either end, `[^\x00-\x1f\x7f-\x9f]` inside | every character above U+009F: non-ASCII spaces anywhere, which are graphic and so legal in a DOI, and format characters, U+2028/U+2029, private use and noncharacters, which ISO 26324 doesn't allow (it takes Unicode's graphic characters) |
| `iri` (`Environment.iri`, `FragmentSelector.conforms_to`) | `` [^\x00-\x20\x7f-\x9f<>"{}\|\\^`%#\u200e\u200f\u202a-\u202e] `` | every character above U+009F but the bidi controls RFC 3987 §4.1 forbids: non-ASCII spaces, the other format characters (U+200B, U+FEFF) and U+2028/U+2029, which RFC 3987's `ucschar` holds, and the characters outside it (§11 item 38) |

### Patterns used once (inline, on their field)

| Field | Says |
|---|---|
| `Output.format` | a lowercase token, `^[a-z0-9][a-z0-9_.+-]*$` (as on `main`) |
| `Input.path` | relative, `/`-separated, no `..` segment, not ending in `/` |
| `AnalysisDeclaration.path` | relative (no leading `/` or `~`); `..` allowed |
| `Option.excluded` | not blank: holds a character of the class `[^\x00-\x20\x7f]` (above) |
| `Evidence.doi` | a DOI name (ISO 26324) in the `10` directory: `10.`, a registrant code of digit runs joined by `.`, `/`, then a suffix with no control character (C0, DEL or C1) and no ASCII space at either end, `^10\.[0-9]+(\.[0-9]+)*/[^\x00-\x20\x7f-\x9f]([^\x00-\x1f\x7f-\x9f]*[^\x00-\x20\x7f-\x9f])?$`. It accepts ISBN-As (`10.978.8889637/173`) and spaces inside the suffix; it rejects a shortDOI (`10/aabbe`) and any other directory indicator (`11.1/x`) (§11) |
| `FragmentSelector.value` | the characters of a fragment identifier, `%` only before two hex digits, ``^([^\x00-\x20\x7f"#%<>\[\\\]^`{\|}]\|%[0-9A-Fa-f]{2})+$`` (no ASCII space or control, none of ``"#<>[\]^`{\|}``); its syntax, the one `conforms_to` names or else a PDF fragment (RFC 8118), isn't checked |

`AnalysisDeclaration.url` takes one of git's two remote forms:
`scheme://…` (`https://github.com/owner/analysis`, `ssh://git@host/x.git`,
`file:///srv/repo`) or scp-like `[user@]host:path` (`git@github.com:owner/repo`),
with the pattern `^(?:[A-Za-z][A-Za-z0-9+.-]*://[^\x00-\x20\x7f]+|(?![A-Za-z][A-Za-z0-9+.-]*://)(?:[^\x00-\x20\x7f/@:]+@)?[^\x00-\x20\x7f/@:]+:[^\x00-\x20\x7f]+)$(?!\n)`.
A value that starts `scheme://` must have something after `://`.
A `url` holds no ASCII space or control character, though git fetches a
remote with a space: a space is written `%20` in a `scheme://` URL, which git
decodes, and since git doesn't decode the scp-like form,
`[user@]host:my dir/x` is written `ssh://[user@]host/~/my%20dir/x` (§11
item 21).
A bare word or a local path (`a`, `owner/repo`, `../repo`) fails:
an analysis in the declaring analysis's repository is declared by `path`,
and another repository on this machine by an explicit `file://` URL.
Whether the URL leads to a valid ASTRA project is the
validator's (`REMOTE_UNREACHABLE`, `MISSING_DECLARED_ANALYSIS`,
`DECLARED_ANALYSIS_INVALID`).

## 5. The analysis document

Every element of `astra.yaml` named by the author is an entry of a map keyed
by its id (D2, D4). "Map" below means that.

### `analysis.yaml`

| Class | Fields | Removed |
|---|---|---|
| **Analysis** | `spec_version` (required), `label`, `description`, `tags`, `inputs` (map of Input), `outputs` (map of Output, required, at least one), `decisions` (map of Decision), `analyses` (map of AnalysisDeclaration), `universes` (map of Universe), `prior_insights`, `findings` (maps of Insight), `container` (untouched) | `id`, `name`, `version`, `path`, inline sub-analyses |
| **AnalysisDeclaration** | `path`, `url`, `commit`. Exactly one of `path` and `url` (`exactly_one_of`); `url` requires `commit` (rule) | – |
| **Input** | `label`, `description`, `tags`, `path` (required) | `type`, `source`, `ref`, `ref_version`, `use_outputs`, `from`, and its rules |
| **Output** | `label`, `description`, `tags`, `type` (required, OutputType), `format` (required), `inputs` (list of `reference`), `decisions` (list of `address`), `when` (list of `condition`), `recipe` | `from`, and its rules |
| **Recipe**, **Resources** | untouched, except that `command`'s description gives the placeholders as RFCs 0003/0004 write them (`{inputs.<entry>}` with the entry exactly as written, dots and `#` included) | – |
| **Decision** | `label`, `rationale`, `tags`, `when`, `options` (map of Option, required, at least one) | `default`, `from`, and its rules |
| **Option** | `label`, `description`, `tags`, `insights` (list of `id`), `requires`, `incompatible_with` (lists of `option_reference`), `excluded` (the reason) | `excluded_reason` |
| **Universe** | `label`, `description`, `tags`, `derived_from` (`id`), `decisions` (map of DecisionSelection, compact) | `analyses` |
| **DecisionSelection** | key `decision` (`address`), `option` (`id`) | – |
| **OutputType** | `metric`, `figure`, `table`, `data`, `report` | – |
| ~~KeyValuePair~~, ~~InputType~~, ~~UniverseNode~~ | – | removed |

neither are a universe's `tags`.

### `insight.yaml`

| Class | Fields | Removed |
|---|---|---|
| **Insight** | `label`, `claim` (required), `description`, `evidence` (list of Evidence, required, at least one), `scope`, `tags` | `created_at`, `derived`, `notes` (now `description`) |
| **Evidence** (a list item) | `doi`, `artifact` (`reference`), `version` (integer ≥ 1), `quote` (TextQuoteSelector), `location` (FragmentSelector). Exactly one of `doi` and `artifact`; `version` only with `doi` | `id`, `snapshot`, `source_commit` |
| **TextQuoteSelector** (`oa:TextQuoteSelector`) | `exact` (required, `oa:exact`), `prefix` (`oa:prefix`), `suffix` (`oa:suffix`) | – |
| **FragmentSelector** (`oa:FragmentSelector`) | `value` (required, `rdf:value`) and `conforms_to` (`dcterms:conformsTo`, an `iri`): a fragment in the syntax `conforms_to` names, a PDF fragment (RFC 8118, `page=6`) when it is absent | `page` |
| ~~InsightCollection~~ | – | removed |

`conforms_to` is optional (tidy-up change 4); without it the syntax is
PDF's, so a location written before it keeps its meaning. Web Annotation
names that syntax by the RFC 3778 IRI, and writing that IRI means the same as
writing none. With both a `quote` and a `location`, the quote is sought within
the location (`oa:refinedBy`).

## 6. The provenance record

| Class | Fields | PROV-O |
|---|---|---|
| **ProvenanceRecord** | `spec_version`, `address` (`reference`), `content_hash`, `size` (integer ≥ 0), `generated_by` (Generation), all required | `prov:Entity`, standing for the result; `generated_by` is `prov:wasGeneratedBy` |
| **Generation** | `commit`, `environment`, `runner` (required); `inputs` (list of RecordedInput); `started`, `finished` (`timestamp`, optional) | `prov:Activity`; `inputs` and `environment` are `prov:used`, `runner` is `prov:wasAssociatedWith`, and the times are `prov:startedAtTime`/`prov:endedAtTime` |
| **RecordedInput** | `entry` (`reference`), `content_hash`, `size`, all required | `prov:Entity` |
| **Environment** | `iri` (required, the class's `identifier`, an `iri`, never a CURIE) | `prov:Entity`, the `@id` of which is the IRI exactly as written |
| **Runner** | `id`, `version` (required) | `prov:SoftwareAgent`; `version` is `schema:softwareVersion` |

- `spec_version`, `address`, `content_hash`, `size`, `commit`, `entry` and
  `runner.id` are `astra:` terms, since PROV has none.
- Read as RDF (spec §10), the root node stands for the result, which the run
  generated: its `address`, `content_hash` and `size` describe the result, and
  its `spec_version` describes the record (§12: a `prov:Bundle` would separate
  the two).
- `inputs` is required when the output lists inputs. That depends on
  `astra.yaml`, so it's a check rule (§7), not a schema rule.
- `inputs` stays the list RFC 0005 gives: one item for each entry the output
  lists in the `astra.yaml` files at the record's `commit`, and no other item,
  matched by `entry`; their order carries no meaning (`MISSING_RECORD_INPUTS`).
  A later change to the list makes the result `stale`, not `missing` (RFC 0005
  §4).
- `commit` is the commit the recipe ran from, a commit of the repository the
  record is committed in (RFC 0005 §3 and RFC 0007 §4 read together): the
  submodule's own commit for a result that belongs to an analysis in a
  submodule, and the driver's commit for what a driver's universes build
  (RFC 0007 §7). It pins every `astra.yaml` in that repository, an analysis
  in a submodule of it through the commit the submodule is pinned at, and an
  analysis from a commit through its declaration's `commit`.
- A checker reads records only through planned results: a record at no
  planned result's place gets no status, and no check rule applies to it
  (RFC 0005 §4).

## 7. Validation layers and the rule catalogue

### Layers

| Layer | Enforced by | Sees |
|---|---|---|
| **parse** | a YAML 1.2 loader under the core schema, plus §3's checks (`astra.yaml`), or a strict JSON parser (records, §3) | one file's bytes |
| **schema** | the generated JSON Schema | one file's data |
| **validator** | a semantic validator | every `astra.yaml` of the analysis stack, and git (spec §3); no results |
| **check** | a results checker | every `astra.yaml` of the analysis stack, now and at each record's commit, and git (spec §3); records and results |
| **runner** | whatever runs recipes | its own actions, the checkouts it runs recipes in, and what the recipes read |

### How a rule is written

**The rule is always what must (or should, or may) hold. What you get when it
is broken is always in a column of its own.** This is true in every layer:

- **Rule:** one sentence saying what holds in a conforming file, record or
  run. It is in the present tense, and its subject is what the rule is about
  ("A declaration has …", "Every pin names …", "No output …"). It never says
  what happens when it is broken.
- **Level:** `MUST`, `SHOULD` or `MAY` (RFC 2119), applied to that sentence,
  and `MAY` only in the runner table.
- **Code:** names what is wrong when the rule is broken. It is what a tool
  reports.
- **Source:** the RFC section, or a decision of this design.

What breaking a rule leads to depends on the layer:

| Layer | When a rule is broken |
|---|---|
| parse, schema, validator | A broken `MUST` is reported as an **error** and makes the file invalid (a checker reports a record's as a reason of `INVALID_RECORD`); a broken `SHOULD` is reported as a **warning**, and the file stays valid |
| check | Nothing fails. The code is reported and **the result gets a status**, given in the check table's extra column, *Status when broken* |
| runner | A runner that breaks a `MUST` doesn't conform. It runs no recipe while `UNCOMMITTED_CHANGES` would be broken, and builds no output while `STALE_INPUT` would be, and when it refuses for either it reports the code. `UNDECLARED_READ` binds the recipe: breaking it leaves the analysis valid, and a runner that enforces it fails the recipe and reports the code |

The check layer is the only one laid out differently, with that extra
column, because breaking one of its rules changes what a result is. A parse,
schema or validator rule decides whether a file is valid, and only through
its `MUST`s.

A `MAY` row states what a tool may do. Leaving it out breaks nothing and
makes no tool non-conforming. The code is what a tool that does it reports.
Only the runner table, whose rules are about a tool's own actions, can have
`MAY` rows.

A tool reports every rule broken, except where another broken rule leaves what
a rule is about undetermined: spec §9's *What is checked* lists those cases,
closed (§11 item 28).

Codes reuse astra-tools' names (on its `main`) where the meaning hasn't
changed: `EXCLUDED_OPTION_SELECTED`, `INACTIVE_DECISION`,
`INCOMPATIBLE_OPTIONS`, `INVALID_INSIGHT_REF`, `MISSING_DECISION`,
`MISSING_REQUIRED_OPTION`, `OUTPUT_CYCLE`, `UNDECLARED_TEMPLATE_REF` and
`UNKNOWN_OPTION`. Its per-field reference codes (`INVALID_OUTPUT_INPUT`,
`INVALID_WHEN_REF`, …) merge into `UNRESOLVED_ADDRESS`, and
`DUPLICATE_INPUT`/`DUPLICATE_OUTPUT` into `DUPLICATE_KEY`. The specification's
catalogue (§8, section 9) is this list in final form.

### check

Read this table like the others: **the Rule column says what must hold**.
The extra column, **Status when broken**, is what the result gets when the
rule doesn't hold. A result for which every rule holds is `unchanged` and
`present`.

**Statuses.** A checker gives every planned result two statuses, one for its
record (`unchanged`, `stale` or `missing`) and one for its bytes (`present`
or `absent`). A result of an analysis from a commit that no recipe reads has
only the first. Evidence citing a result gets that result's first status. A
result with two names has its statuses at each place. Evidence citing an
output built per universe without a pin gets the worst first status of that
output's results (`missing`, then `stale`), and `missing` when there are
none.

| Status | Means |
|---|---|
| `unchanged` | The result has a valid record where its address says, and `STALE_RESULT` holds |
| `stale` | The result has a valid record where its address says, and `STALE_RESULT` doesn't hold. The checker says what changed |
| `missing` | The result has no valid record where its address says: `MISSING_RECORD`, `INVALID_RECORD` (including a record that breaks a parse or schema rule), `MISPLACED_RECORD` or `MISSING_RECORD_INPUTS` doesn't hold |
| `present` | The bytes at the result's default place hash to the record's `content_hash` and have its `size` |
| `absent` | Anything else is at the default place, nothing, a stand-in or other bytes included |

**Rules.**

| Code | Level | Rule | Status when broken | Source |
|---|---|---|---|---|
| `MISSING_RECORD` | MUST | Every planned result has a record at `.astra/records/{universe}/{name}.json` (or `{name}.json` for an output built once), for each of its names, in the analysis it belongs to | `missing` | 0005 §1 |
| `INVALID_RECORD` | MUST | The record at each planned result's place breaks no parse rule, states a `spec_version` whose minor version has a record schema or is greater than the checker's, and breaks no schema rule against that minor version's record schema, or against the open variant when that minor version is greater than the checker's | `missing` | 0005 §2, tidy-up, D10 |
| `MISPLACED_RECORD` | MUST | The record at each planned result's place has, as its `address`, the address that place is worked out from | `missing` | 0005 §1 |
| `MISSING_RECORD_INPUTS` | MUST | The record at each planned result's place has exactly one `inputs` item for each entry its output lists at the commit the record names, matched by `entry`, and no other item (their order carries no meaning) | `missing` | 0005 §2 |
| `STALE_RESULT` | MUST | Since the commit in a result's record, nothing has changed in its output's declaration (command, inputs and their order, decisions, format), its decisions' options, the content of its inputs, never what stands in for it, or the results it reads | `stale` | 0005 §4 |
| `ABSENT_RESULT` | SHOULD | Every result's recorded bytes are at its default place | `absent` | 0005 §1 |
| `STALE_EVIDENCE` | MUST | Every evidence citing a result cites an unchanged one | the cited result's status; without a pin on an output built per universe, the worst of its results' (`missing`, then `stale`) | 0005 §5 |

The results of an analysis from a commit that are read or cited get their
record status (`unchanged`, `stale`, `missing`) by the same rules, through
their records at the declared commit. Only those a recipe reads get a bytes
status (`ABSENT_RESULT`), from what git holds at the declared commit (0007
§4–5).

## 8. The specification

`docs/specification.md` is replaced by the normative text. The explainer it
holds today stays in git history for the docs project.

- **Keywords:** RFC 2119/8174, normative only in capitals.
- **Notation:** ABNF (RFC 5234).
- **Fields:** linked to the generated reference, never restated.

Sections:

1. **Conventions:** keywords, terms, notation, `spec_version`. Versions are
   ordered as integers, MAJOR, then MINOR, then PATCH, and patch releases
   never change what is valid, so each minor version has one analysis schema
   and one record schema. A checker has the record schema of every minor
   version from 0.1 up to its own (spec 2). What one minor version promises
   another is left to the versioning policy.
2. **Overview:** what ASTRA records, the two documents, and the four
   conforming roles: document, validator, checker, runner.
3. **Files:** `astra.yaml` is YAML 1.2 and invalid with duplicate keys.
   Records are JSON. Locations: `astra.yaml`, `.astra/records/…`,
   `results/…`.
4. **Names and grammars:** §4's ABNF, and how an address resolves through
   declarations.
5. **The analysis:** inputs, outputs (`type`, `format`, placeholders),
   decisions and options (constraints, `excluded`), conditional elements
   (`when` as on `main`), insights and evidence.
6. **Universes:** declaration, `derived_from`, the effective selection, and an
   output built per universe or built once.
7. **Composition:** declarations, the analysis stack, driving and consuming,
   pins across analyses, analyses from a commit.
8. **Results and records:** where results belong, where records and bytes go,
   what a record holds, and the statuses.
9. **Conformance:** §7's catalogue, one table per layer. The only place a rule
   is stated as a rule. Earlier sections link to it.
10. **Schema artefacts:** the files, their `w3id.org/astra` URIs, and which one
    is the contract.

## 9. Testing (this phase: the schema layer)

- **`rules.json`:** the harness checks each invalid fixture's error through
  `rules.json` (its absolute keyword location maps to the fixture's `# rule:`
  code), so the tests read what the tools read (D13).
- **Fixtures:** `tests/data/{valid,invalid}/<Root>-<nnn>-<what>.<ext>`, where
  `<Root>` is `Analysis` (an `astra.yaml`, `.yaml`) or `ProvenanceRecord` (a
  record, `.json`). Each is a whole document. Each invalid fixture is a
  minimal valid document with one thing broken, and starts with
  `# rule: <CODE>`, the rule it breaks. A record can't hold a comment, so its
  header lines are in a sidecar, `<Root>-<nnn>-<what>.header`.
- **One validation path:** every fixture is validated by a plain `jsonschema`
  2019-09 validator against the committed generated schema, as a consumer
  would. No LinkML is involved.
- **Failing for the right reason** (Ruling R24): an invalid fixture starts with
  `# rule:` and `# fails at: <JSON Pointer>`. The test asserts that the errors
  are reported there and nowhere else, that `rules.json` gives them the rule,
  and that the rule is a parse/schema code; a parse fixture's loader error
  gives exactly its code (a repeated key `DUPLICATE_KEY`, any other
  `INVALID_SYNTAX`). A second error is allowed only where the fixture declares
  it, in a third line `# also: <CODE> at <JSON Pointer>`: the errors there must
  be reported, and `rules.json` must give them that code.
- **Parse:** the harness loads YAML as YAML 1.2 under the core schema only
  (Ruling R19): `no`/`yes`/`on` stay strings, timestamps stay strings, `<<` is
  an ordinary key, `1_000` is a string, no `!!set`/`!!binary`/`!!omap`, a
  `%YAML` directive other than 1.2 is an error, duplicate keys raise (PyYAML is
  YAML 1.1 and keeps the last duplicate silently; ruamel's stock safe loader
  still resolves timestamps and merge keys), and a fixture with a duplicate
  key fails at parse (`# fails at: parse`). That fixture is excluded from the
  repository's own YAML linters (`yamllint`, pre-commit's `check-yaml`). A
  value with no JSON form raises too: a number that isn't finite or is beyond
  a double's range, and a string holding a lone surrogate (an escaped
  surrogate pair is one character). An entry whose key isn't a string is left
  out and its key reported (`load_document`): the invalid-fixture test counts
  it as `INVALID_ID` at its map, not through `rules.json`, and `load_yaml`
  raises on it, so no valid document has one. The harness reads a file's
  bytes as strict UTF-8 (a byte order mark may start it), and reads YAML
  1.2.2's characters, tabs and line breaks where ruamel.yaml departs from
  them: a tab separates wherever YAML allows white space outside indentation,
  and is refused in indentation; NEL, LS and PS are ordinary characters; a
  quoted scalar takes any character but a C0 control, and a plain scalar, a
  block scalar or a comment refuses DEL, the C1 controls but NEL, U+FEFF,
  U+FFFE and U+FFFF. It is checked against yaml-test-suite: its error cases
  each raise, and its well-formed cases that hold a tab, vendored with their
  `in.json`, each load to it. A fixture that the linters' loaders refuse (a
  tab, a C1 control, bytes that aren't UTF-8) is excluded from them too.
- **Records:** the harness reads a record as spec §3 does (`load_json`):
  strict UTF-8 with no byte order mark, then `json.loads` with hooks that
  refuse a repeated name (`DUPLICATE_KEY`), `NaN` and `Infinity`, and a
  number beyond a double's range, and a walk that refuses a lone surrogate
  (`INVALID_SYNTAX`). Record parse fixtures cover each, and a comment, a
  trailing comma, a byte that isn't UTF-8 and YAML's block form. The
  specification's JSON examples are read the same way.
- **The extension:**
  - fixtures for a bad map key, the string shorthand and a null value
  - a structural test that walks the generated schema and asserts that every
    id-keyed map has `propertyNames` and its one value form
- **Drift:** regenerate into a temporary directory and compare with what's
  committed.
- **Ajv:** `just check-ajv` compiles the three committed JSON Schemas under
  `strict: true`, with the Ajv pinned in `tools/ajv/`. CI runs it.
- **Spec §10's filter:** `tests/test_rules.py` applies it to the standard
  output of jschon (pinned in the dev group) for each schema-layer invalid
  fixture, both its basic output and every failing unit of its verbose
  output, subschemas included: every error kept has an entry, and the
  (pointer, code) pairs are `jsonschema`'s. On Analysis-150 and Analysis-166 the verbose output lists
  what the filter drops: a failing branch of a `oneOf` that passes, an `if`
  whose `then` doesn't fail and the `not` inside it.
- **Lint:** `linkml-lint` is clean.
- **Examples:** every `astra.yaml` under `examples/` validates.
- **The open variant:** a record with an unknown field fails the closed schema
  and passes the open one.

18. A result's bytes are `present` or `absent`, and tools may report more:
    `modified` is not a status. RFC 0005 §1's MUST on what a result's default
    place holds is broken as `absent` (`ABSENT_RESULT`). Tidy-up change 9, *The
    `modified` status is removed*.
19. `spec_version`, in an analysis and in a record, has three parts,
    `MAJOR.MINOR.PATCH`, without leading zeros, such as `0.1.0` (`main` also
    took two parts and leading zeros, such as `1.0` and `01.1.0`, and RFC 0005
    gives only the example `0.1.0`). Specification and schema only.
20. `Evidence.doi` is a DOI name (ISO 26324) in the `10` directory: `10.`, a
    registrant code of digit runs joined by `.`, `/`, and a suffix with no
    control character (C0, DEL or C1) and no ASCII space at either end. It
    accepts every ISBN-A (`10.978.8889637/173`), which `main`'s
    `^10\.\d{4,}/.*$` rejected, and spaces inside the suffix
    (`10.3929/ethz-a- 007549606`). Where `main` took any suffix, it rejects an
    empty one, a control character and an ASCII space at either end. It also
    rejects two forms ISO 26324:2022 allows: a shortDOI (`10/aabbe`), which
    doi.org resolves, and any other directory indicator (`11.1/x`), which no
    resolver serves. A shortDOI is an alias for a full DOI, and tools compare
    DOIs as strings, so a work is cited by its full DOI, under one name.
    Specification and schema only.
21. What the character classes admit above U+007F (spec §4, and the table
    in §4 here). `Option.excluded` and `AnalysisDeclaration.url` take
    `[^\x00-\x20\x7f]`, which admits non-ASCII spaces, format characters,
    U+2028/U+2029 and the C1 controls, so a reason made only of them is not
    blank (the draft's change 14, *`excluded` holds the reason*, gives this
    range). The suffix of an `Evidence.doi` takes `[^\x00-\x20\x7f-\x9f]` at
    either end and `[^\x00-\x1f\x7f-\x9f]` inside, which admit format
    characters, U+2028/U+2029, private use and noncharacters: ISO 26324
    excludes them, and no rule checks them. A `url` holds no ASCII space or
    control character, though git fetches a remote with a space (RFC 0007 and
    the draft's change 28, *A `url` is a remote's URL*, don't say which
    characters a `url` holds): a space is written `%20` in a `scheme://` URL,
    which git decodes, and since git doesn't decode the scp-like form,
    `[user@]host:my dir/x` is rewritten `ssh://[user@]host/~/my%20dir/x`.
    Specification and schema only.
22. `PIN_LIKE_COMMENT` is removed. RFC 0003 recommends a warning on an input
    whose line comment looks like a pin (`- f1_score #svm`), and nothing says
    what looks like one; a validator reads a file's data, not its comments.
    Spec §4 keeps the stray space as advice to authors: a pin is written with
    no space before its `#`. Tidy-up change 8, *The warning on a comment that
    looks like a pin is removed*.
23. A value with no JSON form makes a file invalid. A key that isn't a string
    is `INVALID_ID` at its map, and its entry is left out. A non-finite
    number, one beyond a double's range, and a lone surrogate are
    `INVALID_SYNTAX`. This states the draft's change 36 (*Files are YAML
    1.2*), "a file means the same as the JSON it converts to", and needs no
    text of its own. Specification only.
24. A record is strict JSON, judged as a document: RFC 8259 JSON text in
    UTF-8 with no byte order mark, using only JSON's forms (no comment,
    trailing comma, `NaN` or `Infinity`), all `INVALID_SYNTAX`, with no name
    written twice in an object (`DUPLICATE_KEY`, which `json.loads` and
    `JSON.parse` don't report), and its strings and numbers as item 23 has
    them. A record that breaks a parse or schema rule leaves its result
    `missing`: a checker reports `INVALID_RECORD`, with the parser's code, or
    the one `rules.json` gives the schema error, as its reason. RFC 0005 says
    only that records are `.json` files (its §1), judged in the check layer
    (its §2), and the draft's change 25 (*A record holds only its version's
    fields*) only that a field its version doesn't define makes a record
    `missing`. Specification only.
25. An `astra.yaml` is UTF-8, and may start with a byte order mark but holds
    none anywhere else outside a quoted scalar (YAML 1.2.2 §5.2 also allows
    UTF-16 and UTF-32, and a byte order mark at the start of each document;
    the draft's change 36, *Files are YAML 1.2*, names no encoding).
    Otherwise its characters, tabs and line breaks are YAML 1.2.2's, which
    spec §3 states without changing a verdict. Migration: re-save a UTF-16 or
    Latin-1 file as UTF-8, and delete a byte order mark that doesn't start
    the file and isn't in a quoted scalar. Specification only.
26. A universe's own `decisions` give each decision one key, and no list holds
    two spellings of one entry (`DUPLICATE_ELEMENT`); RFC 0004:221 allows
    agreeing spellings. A derived universe can still set a decision it
    inherits under another spelling (spec §4, §6, §7). Tidy-up change 33, *One
    spelling of each entry*.
27. Driving and pins are defined once (spec §6, §7, §8), where RFC 0004
    leaves each point open. A derived universe sets each of its own
    selections on the decision, so every inherited key for it takes the new
    option. A universe drives a declaration when a key in its effective
    selection goes through every declaration from its analysis's file to
    that one, and each chain of declarations, two that end in one
    declaration included, is driven by all of an analysis's universes or by
    none (`PARTIALLY_DRIVEN`). An analysis with no decisions and no
    universes of its own is driven by every universe that drives the chain
    before it, unless its declaration leads back to an analysis already on
    the chain, itself included, so RFC 0004's
    `subanalysis3.output3_per_universe` is built in the root's universes
    when it is planned (spec §8), though in RFC 0004's example nothing reads
    it, so it isn't built (item 32); one with universes of its own keeps
    them unless a key drives it. An unpinned read or a consumed decision in
    the file of the analysis whose
    universe is being built needs the address's chain driven, up to its last
    declaration (`UNDRIVEN_DECLARATION`). A pin resolves in the file it is
    written in, and names a universe of the first analysis along its
    reference, from that file's own, whose universes drive the reference's
    declarations from that analysis's file to its last, or else of the
    analysis whose output it is (`UNKNOWN_PIN_UNIVERSE`). Tidy-up change 32,
    *Driving and pins are defined once*.
28. A rule isn't checked where another broken rule leaves what it is about
    undetermined. Spec §9's *What is checked* lists the cases, closed. Every
    case starts from a broken `MUST`, so it changes which codes are reported,
    never validity. Specification only.
29. Git is read one way (spec §3, *Reading git*): the work tree without
    `.git`; symlinks never followed, so a symlink is an input's file only as
    a stand-in the validator recognises and never a declared analysis;
    gitlinks crossed at a commit, never for tracking; the innermost
    repository; the index for tracked, so a staged input passes and one in a
    plain data submodule fails `INPUT_NOT_TRACKED`; HEAD or MERGE_HEAD for
    the working tree's commit (`COMMIT_NOT_ANCESTOR`); a submodule's URL from
    `.gitmodules` at the commit; blobs unfiltered, so an `astra.yaml` at a
    commit is parsed from its blob. RFCs 0004, 0006 and 0007 leave all of it
    open. Specification and schema only, except that a path crosses a gitlink
    at a commit, where the submodule's commit is got from, and what failing to
    get it reports: tidy-up change 35, *A submodule's commit is got like a
    remote's*.
30. Getting a commit from a remote is checked each time, a kept copy counts
    as got, and a commit that can't be got is reported on the outermost
    declaration in a file outside every analysis from a commit (spec §7,
    *Validity*; `REMOTE_UNREACHABLE`). RFC 0007 §6 says the answer can't
    change: the rest of it can't, and a validator can still remember it.
    Specification only.
31. A validator checks every universe of every analysis of the stack, a
    driven analysis's own included (spec §2, §7, *Driving and consuming*,
    §9). Each universe's selections are held to spec §6 and to driving, so
    where the root drives `sub`, a universe of `sub`'s own that leaves an
    active decision of `sub` unset breaks `MISSING_DECISION`, and one that
    selects an option its decision doesn't have `UNKNOWN_OPTION`, though the
    root's universes don't use either. The rules on the universe being built
    (`NOT_BUILT_IN_UNIVERSE`, `UNDRIVEN_DECLARATION`, `INPUT_NOT_BUILT`) hold
    only in the universes built, the root's and those a pin names, so a
    stage can keep universes of its own that would break them if built. RFC
    0004 §3 says a driven analysis's own universes "are considered to not
    exist", and leaves open whether a validator checks them. Specification
    only.
32. The planned results are the root's active outputs, what they read,
    transitively, and what its evidence cites (spec §8). An output nothing
    reaches isn't built: RFC 0005:215's `iris_pipeline` has 12 results, not
    14 (nothing reads `feature_plot`), and RFC 0004 §5's and RFC 0005 §1's
    layouts lose `subanalysis3.output3`, `subanalysis3.output3_per_universe`
    and `subsubanalysis1.output1#u2`. A result is named through driven
    declarations only, and one reached through two chains of them is placed
    and recorded under each. Unpinned evidence on a per-universe output gets
    the worst status of its results. RFC 0005 uses "planned" (0005:199)
    without defining it, and gives unpinned evidence no status. Specification
    only.
33. `UNDECLARED_READ` is a SHOULD. RFC 0005 §3 makes it a MUST on the
    recipe, but nothing checks a recipe except a runner that chooses to. The
    analysis stays valid when a recipe breaks it, and a runner conforms
    whether or not it enforces it. Tidy-up change 19, *A recipe should read
    only through its inputs*.
34. `UNCOMMITTED_CHANGES` is judged in the checkout a recipe runs in, which
    can be a clean worktree at the recorded commit while the repository's
    own working tree has changes (spec §8). The runner writes the results
    and records into the working tree, to be committed in a commit that has
    the recorded commit in its history. RFC 0005 §3's rule is 'Only
    committed code is run' (l.161); its 'while the repository has changes'
    (l.149) is one way to keep it. Specification only.
35. Runner-owned places are kept apart (spec §3, §4, §5, §7, §8). RFC 0005
    §1 puts results under `results/` and records under `.astra/`, but
    nothing keeps an analysis's own files out of them, so an input could
    read a result by its path, outside the result graph (no build order, no
    `STALE_INPUT`, no pin), and a run could overwrite an input or a declared
    `astra.yaml` (the v0.1 review's F053). No input's `path` and no
    declaration's `path`, with `.`, `..` and repeated `/` resolved, is or
    lies in the `results/` or `.astra/` of an analysis of the stack
    (`RESERVED_PATH`), and a result is read by its address. An input may
    still name an `astra.yaml`, which no runner writes. RFC 0004 lets an
    output and a declaration share an id, and a format can hold a `.`, so
    the output `stage` in format `summary.json` and the driven result
    `stage.summary` in format `json` had one default place,
    `results/u1/stage.summary.json` (F037). No output shares its id with a
    declaration of the same analysis, driven or not, by `path` or by `url`
    (`CLASHING_RESULT_NAME`), so no two results of one analysis share a
    default place, and `tar.gz` stays a format. Both are `MUST`s: under a
    `SHOULD` a runner couldn't keep `UNRECORDED_RESULT`. Tidy-up change 34,
    *Runner-owned places are kept apart*.
36. Versions are ordered by MAJOR, then MINOR, then PATCH, each compared as
    an integer, so `0.10.0` comes after `0.9.0`, and a version's minor
    version is its MAJOR and MINOR (spec §1). A patch release never changes
    what is valid, so each minor version has one analysis schema and one
    record schema, and every `0.1.x` document is read by 0.1's. A checker
    implements one version, its own, and has the record schema of every
    minor version from 0.1 up to its own (spec §2). It reads a record by its
    minor version's record schema, or by the open variant when that minor
    version is greater than its own, and a record whose minor version is
    smaller and has no record schema, such as `0.0.9`, breaks
    `INVALID_RECORD`, so its result is `missing` (spec §8, §9). RFC 0005 §2
    and the draft's change 25, *A record holds only its version's fields*,
    say only "a later version": no RFC orders versions, or says which record
    schemas a checker has. Specification only.
37. No list of strings is empty (D12). `Output.inputs`, `Output.decisions`,
    `when`, `requires`, `incompatible_with`, `insights` and `tags` each have
    at least one entry where they are written, and a field with nothing to
    list is left out (spec §4, `EMPTY_COLLECTION`). An empty list is a second
    way of leaving a field out, and for `decisions` and `when` it has no
    defined meaning: spec §6 builds an output per universe when it lists
    `decisions` or has a `when`, and `when: []` has a `when` whose zero
    conditions all hold, which JavaScript's `Boolean([])` and Python's
    `bool([])` read differently, so a runner and a checker could put its
    record in different places (the v0.1 review's F006). An empty map, such
    as `universes: {}`, stays valid. RFC 0003 §2 builds an output per
    universe if it "declares `decisions`, has a `when`", and doesn't say
    whether an empty one counts. Tidy-up change 27, *No list of strings repeats
    an entry or is empty*.
38. An environment's `iri` is an IRI as far as its pattern checks (spec §4,
    §8). RFC 0005 says the record schema checks "an IRI for the environment"
    (0005:142), and the `iri` type checks a scheme, `:`, RFC 3987's
    characters, `%` only before two hex digits and at most one `#`. It rejects
    an ASCII space or control, a C1 control, `<>"{}|\^`, the backtick, the
    bidi formatting characters (U+200E, U+200F, U+202A–U+202E), a `%` not
    followed by two hex digits, a second `#`, and an empty part after the
    scheme, so it rejects the IRIs `x:` and `x:#y`. It admits every other
    character, noncharacters, the specials U+FFF0–U+FFFD, the tag characters
    and variation selectors of U+E0000–U+E0FFF and private use included. It
    doesn't check authority, port, IP literals, `[` or `]` outside an IP
    literal, or where private-use characters may stand (RFC 3987 allows them
    only in a query, which a character class can't place), so it accepts
    `urn:x:a[b` and `http://h:x:y/`, which RFC 3987 rejects. A record whose
    `iri` matches the pattern is valid (`INVALID_RECORD` follows the pattern),
    so every checker gives the same verdict without an RFC 3987 parser, and a
    runner writes an RFC 3987 IRI (`UNRECREATABLE_ENVIRONMENT`). No record
    needs migrating, since no tool writes records yet. RFC 3987's full grammar
    as the pattern would close the gap, at the cost of a long pattern in the
    regex subset Python and ECMA-262 share; Tom chose the characters
    (2026-11-04). The same type checks `FragmentSelector.conforms_to`.
    Specification and schema only.

  in a clean checkout of the runner's own while the working tree has
  changes.
- **Check and runner phase:** what the v0.1 review left to checkers and
  runners, as Tom decided it (2026-11-04). Each point lands in the
  specification at that phase, with the RFC that amends RFC 0005 or RFC 0007
  where it needs one; until then the specification follows those RFCs as
  written.
  - *What `STALE_RESULT` compares* (the v0.1 review's F024, F040 and F041),
    for the RFC that amends RFC 0005 §4, and RFC 0007 §4 for the scope:
    - *Against what.* A result of the analysis being checked, or of an
      analysis reached from it by `path` alone, is judged against the working
      tree: the `astra.yaml` files, inputs, results and records on disk,
      committed or not, the frame a validator reads them in (spec §3,
      *Reading git*). A result of an analysis from a commit is judged at its
      declared commit (spec §7). So a runner can read the records it has
      just written, and a chain of builds needs no commit between its steps.
      Not taken: HEAD, under which every result is `missing` right after a
      run.
    - *Which option counts.* The option the universe's effective selection
      gives each of the output's decisions, by its id alone: only the id
      reaches the recipe (`{decisions.<entry>}`). Editing that option's other
      fields, or adding or editing other options, leaves the result
      unchanged. Not taken: the selected option's whole definition, against
      spec §8's "editing … a description … leaves a result unchanged"; the
      selection plus the decision's whole `options` map, RFC 0005 §4's most
      literal reading, which fits both examples, spec §8's and its own, but
      under which adding an option to explore later makes every result of
      the output stale.
    - *A result it reads.* Each is compared by the `content_hash` of its
      current record with the hash in the reader's `inputs`. A result that
      reads one that is `stale` or `missing` is stale, and the checker says
      which, as spec §7 asks of the results an analysis from a commit was
      made from; one that reads an `unknown` result, and that nothing else
      makes stale, is `unknown` (*Content and a commit's files*, below).
      Once that one is rebuilt, the reader is unchanged again if the rebuilt
      bytes are the same. Not taken: unchanged while the hashes match, which
      lets a broken upstream record pass.

    Spec §8's *When a result is unchanged* opens with the frame and takes
    the other two points in its list; the spec's §9 `STALE_RESULT` row
    becomes one sentence with the same scope and the three points, and
    `rules.json` is regenerated. Conformance cases: changing the selection
    makes a result stale, while adding an option or describing the selected
    one doesn't; a reader of a `missing` result is stale; an uncommitted edit
    of an input makes a result stale; and records just written are
    `unchanged`.
  - *What a change is* (the v0.1 review's F045), for the RFC that amends
    RFC 0005 §3. `UNCOMMITTED_CHANGES` is judged in the checkout the recipe
    runs in (§11 item 34):
    - *What counts.* What `git status` reports in that checkout, with the
      files a committed `.gitignore` ignores left out, less one exemption:
      every record, and every result whose bytes match the SHA-256 in its
      record, whichever run wrote them. A hand edit to a result is a change.
      What a tool keeps of, or puts in place to drive, an analysis from a
      commit is exempt only under an analysis's `.astra/` or in an ignored
      place. Not taken: (a) all of every analysis's `.astra/records/` and
      `results/`, which lets a hand edit pass; (b) tracked changes only,
      which runs untracked helper code unpinned; (c) ignored files counting,
      which makes any build cache refuse the run; (d) only what this run
      writes, which forces a commit between runs.
    - *Which ignore rules.* Only the committed `.gitignore` files, the same
      on every machine, whatever each machine's git configuration says: a
      file ignored only by `.git/info/exclude` or `core.excludesFile`
      counts. Submodules are checked whatever `submodule.<name>.ignore` or
      `diff.ignoreSubmodules` say, since a committed `.gitmodules`
      `ignore = all` would hide a submodule off its pinned commit. The
      reference form, in the checkout and in each of its submodules, with
      the exemption applied in each (a runner's record in a submodule
      analysis shows in the parent as ` M sub`):
      `git status --porcelain=v2 --untracked-files=no --ignore-submodules=none`
      for tracked changes, and
      `git ls-files --others --exclude-per-directory=.gitignore` for
      untracked files.
    - Which bytes a checkout of a commit gives is another rule's,
      `CONVERTED_CHECKOUT` (*Content and a commit's files*, below), not this
      one's: a runner refuses a checkout that would give other bytes than
      git stores.

    Spec §8's *What a runner does* and the §9 row take the definition, and
    `rules.json` is regenerated. Spec §5, after the recipe sentence on
    `UNDECLARED_READ`, adds: "A file ignored by a committed `.gitignore`
    isn't pinned by the commit, so a recipe uses one only if it is part of
    the environment or made only from the files at the commit (a bytecode
    cache, say)." Conformance cases: an untracked helper (refuse), a file
    ignored only by `.git/info/exclude` (refuse), an ignored `__pycache__/`
    (run), an earlier run's record and result (run), a hand-edited result
    (refuse), an untracked file in a submodule (refuse), a record in a
    submodule analysis's `.astra/records/` (run), and a run in a clean
    worktree at HEAD while the main checkout has an untracked helper (run;
    its records name HEAD, and a checker on the main checkout reports stale
    a result whose input has an uncommitted edit there).
  - *A record whose commit has left the history* (the v0.1 review's F019),
    for the RFC that adds its row to RFC 0005's checks. A record names a
    commit of the repository it is committed in (spec §8, the v0.1 review's
    F043), and RFC 0005 §3 says that commit has to stay in the history of
    the commits that hold the record. Spec §8 states it, with the `SHOULD`
    to merge rather than squash or rebase, but no rule covers a breach: such
    a record is valid and in its place, so it isn't `missing`, and
    `STALE_RESULT` can't be judged without its commit.
    - *The rule.* Spec §9's check table gains `RECORD_COMMIT_NOT_ANCESTOR` |
      MUST | "The commit a planned result's record names is the commit the
      record is read at, or an ancestor of it, in the repository the record
      is committed in" | `missing` | 0005 §3. The commit a record is read at
      follows *What `STALE_RESULT` compares* and spec §3's *Reading git*: the
      commit that holds the record or, in the working tree, HEAD, or
      MERGE_HEAD during a merge (either passes); for a result of an analysis
      from a commit, the declared commit. A commit the repository no longer
      has breaks the rule too. The checker checks it.
    - *Statuses.* Spec §8's *Statuses*: a result is "`missing` when it has
      no valid record where its address says, or its record names a commit
      outside the history of the commit it is read at". Spec §9's Statuses
      table: `unchanged` is "a valid record where its address says,
      `RECORD_COMMIT_NOT_ANCESTOR` holds, and `STALE_RESULT` holds", `stale`
      the same with "`STALE_RESULT` doesn't hold", and `missing` adds
      `RECORD_COMMIT_NOT_ANCESTOR` to its codes. `STALE_RESULT` isn't
      checked for a result whose record breaks the rule: it follows from
      that error, so case 10 of spec §9's *What is checked* leaves it
      unreported. Case 10 gains the rule itself: a result that breaks
      `MISSING_RECORD`, or whose record breaks `INVALID_RECORD`, isn't
      checked by `RECORD_COMMIT_NOT_ANCESTOR`, whose subject, the commit the
      record names, is then undetermined. `MISSING_RECORD_INPUTS` reads the
      output's entries at the commit the record names, so a commit the
      repository no longer has, which breaks `RECORD_COMMIT_NOT_ANCESTOR`,
      leaves it undetermined too: whether case 10 also leaves it unchecked
      for such a record is settled at the check phase.
    - Spec §8, after the sentence on merging: "A record whose commit has
      left the history is `missing`
      ([`RECORD_COMMIT_NOT_ANCESTOR`](#check))." §1's sentence on the
      recommendations no tool can check stays: how a branch was merged still
      can't be checked, only the outcome.
    - Not taken: a record status of its own for such a record, and advice
      with no rule.

    `rules.json` is regenerated. Conformance cases: a squash-merged record
    is `missing`, with no `STALE_RESULT` reported; a record of a result
    that belongs to an analysis in a submodule, naming the submodule's
    commit, is `unchanged`; a record just written at HEAD is `unchanged`;
    and during a merge, a record whose commit is an ancestor of MERGE_HEAD
    but not of HEAD passes.
  - *Content and a commit's files* (the v0.1 review's F044, F071 and F073),
    for the RFC that amends RFC 0005 §3 and §4 and RFC 0007 §5 and §7. The
    specification relies on a commit's files (`NOT_AT_COMMIT`,
    `Generation.commit`) and on the content of an input or result
    (`content_hash`, `size`, `STALE_RESULT`). Spec §3's *Reading git* reads
    a file at a commit as its blob, for validators and checkers, but nothing
    says which files a driven analysis's recipes run on, which bytes a
    record's hashes are of, or what a checker that can't get an input's
    content gives; spec §5 says only that what stands in for the content
    isn't the content, and that which stand-ins count is the tool's:
    - *Which files.* A commit's files are its tree, with each submodule at
      the commit its gitlink pins, got from the URL `.gitmodules` gives at
      that commit (spec §3, *Reading git*); a driven analysis's recipes run
      in its directory within them, so `../src` reaches what the commit
      holds there. Not taken: the analysis's directory alone.
    - *Which bytes at a commit.* A file's content is the bytes git stores:
      at a commit, its blob, as spec §3's *Reading git* already reads every
      file at a commit. Git's checkout conversions (`text` and `eol`,
      `core.autocrlf`, `ident`, `working-tree-encoding`, a filter) never
      enter it: a checker neither applies nor undoes them, and reads no git
      configuration to do so. A stand-in the tool recognises gives the
      content it names. Not taken: a checkout under the commit's
      `.gitattributes` with `core.autocrlf=false` and `core.eol=lf`, which
      has a checker imitate git's conversions.
    - *Which bytes in the working tree.* The bytes on disk, which are what
      git stores wherever no conversion applies. In a clone whose checkout
      converts (`core.autocrlf=true` with no `-text`), a checker reports what
      is on disk: the input changed and the result's bytes `absent`. At a
      commit it gives the blob's answer. Not taken: the blob git would stage
      from the file, which needs git's conversions.
    - *Who reports a breach.* The runner: it refuses to run a recipe that
      would read an input or result as other bytes than git stores for it,
      other than through a stand-in it recognises (`CONVERTED_CHECKOUT`, a
      new runner `MUST`), so every record's hashes are of stored bytes. The
      `.gitattributes` setting that avoids it is advice with no keyword. Not
      taken: a runner warning; a check-layer rule; a validator `SHOULD`
      reading `.gitattributes`.
    - *Without the content.* `unknown`, a record status beside `unchanged`,
      `stale` and `missing`, for a result whose checker can't get the
      content of an input (a git-annex WORM key without its bytes, say)
      where no stand-in it recognises names its hash and size, or that reads
      an `unknown` result (*A result it reads*, above). Since which
      stand-ins count is the tool's, two checkers can give `unchanged` and
      `unknown`, or `unknown` and `stale`, for one input. Not taken: a
      checker that MUST fetch the bytes or fail; `stale`, which contradicts
      its definition.

    Spec §8's *What a record holds* defines **Content** before "Every hash
    names its algorithm": "A file's content is the bytes git stores for it:
    at a commit, its blob; in the working tree, its bytes on disk", and
    every `content_hash` and `size` is of content. §7's *Driving* defines a
    commit's files before the `NOT_AT_COMMIT` sentence, and its *What is
    read* bullet becomes "the bytes of each result or input file that a
    recipe reads, as git stores them (§8)". §8's *What a runner does* says a
    recipe reads the content of each input and result, that a runner refuses
    where a checkout would give other bytes, and that a runner making its
    own checkout can make one with no conversion; then, as plain advice, to
    set `-text` and no `ident`, `working-tree-encoding` or filter (other
    than a stand-in's) in the `.gitattributes` that apply to an analysis's
    inputs and `results/`, so §1's count of recommendations stays two. §9's
    runner table gains `CONVERTED_CHECKOUT` | MUST | "Every input and result
    a recipe reads has, where the recipe reads it, the bytes git stores for
    it, or is got through a stand-in the runner recognises" | 0005 §3,
    0007 §7, §8, and `NOT_AT_COMMIT` reads "A runner drives an analysis
    from a commit on exactly that commit's files (§7)".

    Spec §8's *When a result is unchanged* says when an input's content is
    unchanged: git holds the same blob at its path at the record's commit
    and now, both commits; its bytes have the record's hash and size; or a
    stand-in the checker recognises names the record's SHA-256 and size, or
    is the same, byte for byte, at both. A recognised stand-in naming
    another hash or size is a change, and anything at the path the checker
    doesn't recognise as a stand-in is read as the file. Otherwise the
    result is `unknown`, never `unchanged`. In the working tree (*What
    `STALE_RESULT` compares*, above), "now" is the file on disk, compared by
    its bytes: a blob's identity counts only between two commits. "How a
    checker finds this out is the tooling's choice" ends "within §8's
    *Content*". Spec §8's *Statuses* and §9's check intro list `unknown`
    after `stale`, and §9's Statuses table gains its row after `stale`:
    "The result has a valid record where its address says, and the checker
    can't tell whether `STALE_RESULT` holds: it can't get the content of an
    input, or of a result it reads, and no stand-in it recognises names its
    hash and size. The checker says which", with
    `RECORD_COMMIT_NOT_ANCESTOR` holding, as for `unchanged` and `stale`
    (above). `STALE_EVIDENCE` passes `unknown` on through the cited
    result's status, and `STALE_INPUT` refuses to build from an `unknown`
    result. The bytes status stays `present` or `absent`: a stand-in at the
    default place is `absent`, whatever it names. In the record schema,
    `content_hash` and `size`, the record's and each input's, are "of the
    content (spec §8)", and `Generation.commit`'s "pins every file of the
    code" links §7's commit's files. Design §7's rows and §10's RFC 0007 row
    ("Bytes git stores at the commit") follow, and `rules.json` is
    regenerated.

    Conformance cases: an input with `eol=crlf`, `ident` or
    `working-tree-encoding` read at a commit gives the blob's status in
    every checker, whatever the reader's git configuration; a runner refuses
    a recipe that reads such an input, or an input in a
    `core.autocrlf=true` clone with no `-text`; a `.gitattributes` change
    alone, with the same blob, leaves a result `unchanged` between two
    commits; and a driven recipe reads `../src` from the commit's tree. As
    tool cases, since which stand-ins count is the tool's: a git-annex WORM
    key without its bytes gives `unknown`, a stand-in naming the recorded
    SHA-256 and size gives `unchanged`, and one naming another gives
    `stale`; and a result reading an `unknown` result is `unknown`, evidence
    citing it gets `unknown`, and, where it is a result of an analysis from
    a commit, a runner refuses to build from it (`STALE_INPUT`).
  - *Bytes are judged only against a valid record* (the v0.1 review's F046),
    for the RFC that amends RFC 0005 §1 and §4. Spec §8's *Statuses* gives a
    result its record status against a valid record where its address says,
    and its bytes status against "its record's hash and size", but doesn't
    say whether a file at the result's record place that breaks
    `INVALID_RECORD` or `MISSING_RECORD_INPUTS` is still its record for the
    bytes. So a `missing` result has no settled bytes status: one checker
    reports `missing` and `present`, another `missing` and `absent`, and
    `ABSENT_RESULT` too. RFC 0005 §4 leans towards a valid record only (its
    `missing` is "no record, or a file breaking a rule of section 1 or 2",
    setting such a file apart from a record), and so does RFC 0007 §5
    ("Their content hash and size are checked against the record"), but
    neither says what such a result's bytes are:
    - *The rule.* The bytes are judged only against a valid record where the
      result's address says: `present` when the bytes at its default place
      have that record's hash and size, `absent` otherwise. A result with no
      valid record has nothing to match: it is `missing`, its bytes are
      `absent` (a result of an analysis from a commit that no recipe reads
      still gets only its record status, spec §8's *Statuses*), and no bytes
      code is reported for it. That includes every result whose record
      breaks `INVALID_RECORD`, whatever its reason (a parse or schema rule,
      say), even where the file's `content_hash` and `size` match the bytes.
      Not taken: judging the bytes against whatever file is at the result's
      record place, valid or not, under which a record that lacks only a new
      input gives `present`; it has to say which broken files still give a
      usable hash (one that doesn't parse, one naming another result), and
      it trusts one field of a file the check layer rejects.
    - *With `RECORD_COMMIT_NOT_ANCESTOR`.* By spec §8's *Statuses* sentence
      and the `unchanged`, `stale` and `unknown` rows as the items above
      word them, a record that breaks only that rule (*A record whose commit
      has left the history*, above) is valid and where its address says. Its
      result is then `missing` while its bytes are judged against it, and
      `ABSENT_RESULT` can be reported for it. But that item also adds
      `RECORD_COMMIT_NOT_ANCESTOR` to the `missing` row's codes, which that
      row lists as what "no valid record where its address says" means.
      Read that way, its bytes are `absent` and `ABSENT_RESULT` isn't
      reported, as for any other `missing` result. Which reading holds is
      settled at the check phase, together with the `missing` row's wording
      and that rule's Status when broken.

    Spec §8's *Statuses*: "… and one for its bytes, `present` when the bytes
    at its default place have its record's hash and size, `absent`
    otherwise." becomes "… and one for its bytes, judged only against a
    valid record where its address says: `present` when the bytes at its
    default place have that record's hash and size, `absent` otherwise. A
    result with no valid record has nothing to match, so its bytes are
    `absent`." The sentences after it stay. Spec §9's Statuses table:
    `present` is "The result has a valid record where its address says, and
    the bytes at its default place hash to that record's `content_hash` and
    have its `size`", and `absent` "Anything else: no valid record, or
    anything other than the recorded bytes at the default place, nothing, a
    stand-in or other bytes included". `ABSENT_RESULT` reads "Every result
    with a valid record has its recorded bytes at its default place", so it
    is never reported for a result with no valid record; §10's `rules.json`
    excerpt (*The rule catalogue*) quotes the row, so its `statement`
    changes with it. The Status when broken of `MISSING_RECORD`,
    `INVALID_RECORD`, `MISPLACED_RECORD` and `MISSING_RECORD_INPUTS` becomes
    "`missing`; bytes `absent`", so that the check table's preface (the
    status a result gets when the rule doesn't hold) stays true: a sentence
    after the Statuses table would say the same but not reach `rules.json`.
    The paragraph after the check table still gives a result of an analysis
    from a commit that no recipe reads no bytes status, so these cells'
    "bytes `absent`", like `ABSENT_RESULT`'s `absent`, holds only for a
    result that gets one. Design §7's check table follows, and `rules.json`
    is regenerated. Case 10 of spec §9's *What is checked* gains nothing
    from this: `ABSENT_RESULT`'s rule is scoped to a result with a valid
    record, so for a result with none the rule is not broken. It is not a
    rule left unchecked.

    Conformance case: a result whose record lacks an `inputs` item, with the
    recorded bytes at its default place, is `missing` and `absent`, and no
    `ABSENT_RESULT` is reported.
  - *In the check layer, a broken `MUST` is an error and a broken `SHOULD` a
    warning, and nothing fails* (the v0.1 review's F097). Spec §9's
    consequence table says what a level leads to in every layer but the
    check layer, whose row says only that nothing fails and the result gets
    a status, and §8's *Statuses* says only that `absent` is not an error.
    So `MISSING_RECORD` (`MUST`) and `ABSENT_RESULT` (`SHOULD`) differ only
    in their status, and two checkers can report a `stale` result one as an
    error and the other as a warning. No RFC amends anything for it: it
    restates RFC 0005 §1's "`absent` (not an error because they may be kept
    elsewhere)" and adds no rule.
    - *The rule.* As in the parse, schema and validator layers, a broken
      `MUST` is reported as an error and a broken `SHOULD` as a warning, and
      nothing fails: what the rule is about gets its *Status when broken*.
      So `stale` and `missing` are errors and `absent` is a warning, and
      evidence citing a `stale` or `missing` result is an error through
      `STALE_EVIDENCE`. Whether a check run that reports an error exits with
      a failure is the tool's. Not taken: check codes with no severity, each
      tool picking one, under which checkers differ; and a broken `MUST`
      failing the check run with a non-zero exit.
    - *With `unknown`.* An `unknown` record status (*Content and a commit's
      files*, above) comes from no broken rule: the checker can't tell
      whether `STALE_RESULT` holds, so it reports no code for the result's
      record status, and so no error, and says which content it can't get.
      The result has a valid record where its address says, so its bytes
      are judged as any such result's (*Bytes are judged only against a
      valid record*, above): where they are `absent`, `ABSENT_RESULT` is
      still reported for it, as a warning. Evidence citing it doesn't cite
      an unchanged result, so it breaks `STALE_EVIDENCE`, whose row stays
      as it is, and gets `unknown` through that row's *Status when broken*,
      as *Content and a commit's files* has it: it is an error.

    Spec §9's consequence table's check row becomes "Nothing fails. A broken
    `MUST` is reported as an **error** and a broken `SHOULD` as a
    **warning**, and **the result gets a status**, given in the check
    table's extra column, *Status when broken*", and the paragraph after the
    table gains "Whether a check run that reports an error exits with a
    failure is the tool's." Spec §8's *Statuses*: "`absent` is not an error"
    becomes "`absent` is not an error: [`ABSENT_RESULT`](#check) is a
    `SHOULD`, reported as a warning." Design §7's consequence table and the
    paragraph after it follow. No row's level changes, and `rules.json`
    doesn't: a check code's severity follows its level, which `rules.json`
    already gives, so `just gen-schema` leaves it as it is.

    Conformance cases: a planned result with no record gives
    `MISSING_RECORD` as an error, and one whose recorded bytes are kept
    elsewhere gives `ABSENT_RESULT` as a warning.
- **Docs:** the explainer, `getting-started.md`, `cli.md`, `llms.txt`,

- **Versioning policy:** a patch release never changes what is valid (Tom,
  2026-11-04; spec §1). Versions are ordered by MAJOR, then MINOR,
  then PATCH, each compared as an integer (spec §1; §11 item 36). There is
  one analysis schema and one record schema per minor version, at
  `https://w3id.org/astra/X.Y/` (spec §10), and a 0.1 validator accepts
  every `0.1.x` file. A checker implements one version, its own, and has the
  record schema of every minor version from 0.1 up to its own (spec §2): it
  gets an earlier minor version's from its published URI, and astra-spec
  ships only its own, with no per-release copies. A record of a greater
  minor version is read through the open variant, and one whose minor
  version has no record schema, such as `0.0.9`, breaks `INVALID_RECORD`
  and is `missing`, with no code of its own (spec §8, §9). `just release`
  checks the schema layer of a patch against its minor version's greatest
  release (`tools/check_patch.py`), so each patch's schemas accept what its
  `X.Y.0`'s accept; the validator and check layers rest on review. Moving
  `0.0.x` files to 0.1 is migration. What a minor or a major release may
  change stays for the policy. `spec_version` only checks the format here.
- **Folder formats:** a result is one file (spec 8), as an input is (spec 5).
  A format that is a folder, such as Zarr, is for a later RFC, for results as
  RFC 0006 leaves it for inputs.
- **What v0.1 can't write,** for a later RFC. The first two are limits
  astra-tools met in planning the migration of unions-bmodes-mystra (its
  design §15, §16):
  - *Parametric outputs.* The specification has no way to write one output
    per value of a parameter, so a project generates its outputs and
    repeats them: unions-bmodes-mystra has 351 in one generated file.
  - *Inputs of several files.* An input names one file (spec 5). An input
    that stands for many files becomes one input per file, or an output
    whose recipe reads them all. It sits beside *Folder formats*, above.
  - *Re-exports* (Tom, 2026-11-04). Building a declared analysis's result on
    request (`materialise u1 sub.out`) is the tooling's (*Tooling*, above). A
    later RFC may let an analysis name what it exports: preferably an
    optional `Analysis.targets` list, or else an output with no recipe and a
    single input, read as a re-export. v0.1 gives an output with no recipe
    no meaning (spec §5).

  - *The record as RDF:* the root node stands for the result and also carries
    the record's `spec_version`, so one of its properties describes another
    thing. A later reading can separate the record from the result, the
    record a `prov:Bundle` (a named set of provenance descriptions, itself an
    entity) holding the result's provenance.
  - *Upstreaming the generator extension:* the compact form as an opt-in
    annotation rather than inferred from slot count; `use_curies` support;
    `propertyNames` from the key's whole value schema, not only its pattern;
    `uniqueItems` decided by list type rather than range.
  - *Tidy-up RFC:* `Runner.id`, `Runner.version`, `Insight.claim` and
    `TextQuoteSelector.exact` accept `""`; an `iri` admits the invisible
    characters RFC 3987 allows: non-ASCII spaces, format characters other
    than the bidi controls (U+200B, U+FEFF) and U+2028/U+2029 (spec §4).
  - *Tests:* build the wheel once per run; the pattern guard as a whitelist
    (inline flags, `\p{…}` and similar slip through a blacklist); nested
    combinators in the harness's error walk; the spec-example test parses at
    collection time.
  - *`rules.json` (Task 12):* the unused-`rule`-annotation check looks at
    top-level elements only, not inside expressions (an `exactly_one_of`
    branch's slot condition, a rule's pre- or postconditions), so CLAUDE.md's
    "every `rule` annotation must give some keyword its code" claims a little
    more than the check does; the test harness imports `tools/rules.py` (and so
    LinkML) for its JSON Pointer helper.
  - *Editorial:* concision cuts in the specification; the two `load.py`
    commands and label casing in the examples; a fixture name
    (`ProvenanceRecord-205`) that no longer describes it.

## 13. Open points

- ~~**Agreeing spellings.**~~ **Settled:** two spellings of one decision in
  a universe's own `decisions`, agreeing or not, are an error, and so are two
  spellings of one entry in a list (`DUPLICATE_ELEMENT`, tidy-up change 33;
  §11 item 26). RFC 0004:221 allows agreeing spellings, and its open question
  (:688) asked only whether they should warn. A derived universe can still
  set a decision it inherits under another spelling.
- ~~**`when` on an inactive decision.**~~ **Settled** by the
  conditional-elements RFC draft (#93; Tom, 2026-11-04): a condition that
  names a decision switched off in a universe is an error there unless it is
  guarded, by another condition of the same `when` that fails in that
  universe. The specification takes it when that RFC lands, and until then
  states `main`'s semantics and says no more (§1).
- ~~**An analysis with no decisions, reading a per-universe output.**~~
  **Settled:** an analysis with no decisions and no universes of its own is
  driven by every universe that drives the chain before it, and so by every
  universe of the driver when the driver's file declares it, unless its
  declaration leads back to an analysis already on the chain, itself
  included (tidy-up change 32; §11 item 27). So, as RFC 0004 §3–§4 has it,
  its output that reads one built per universe without a pin is built in the
  root's universes when it is planned (spec §8), and recorded there, as RFC
  0005 §1 has `subanalysis3.output3_per_universe`, while `output3` is still
  built once, when it is planned, and belongs to `subanalysis3`. In RFC
  0004's example nothing reads either, so neither is built, and the RFC 0004
  §5 and RFC 0005 §1 layouts lose both (§11 item 32). An analysis with
  universes of its own keeps them unless a key drives it. The bound keeps names finite: without it, such
  an analysis `x` that declares `self: {path: .}` would be driven as
  `x.self`, `x.self.self` and so on, each a name for its results.
- ~~**A driven analysis reading its driver's elements.**~~ **Settled:** the
  analysis whose universe is being built is always built in it, and
  `UNDRIVEN_DECLARATION` applies only in its file (RFC 0004:411), so an
  analysis it drives consumes its decisions and reads its outputs back
  through `..` (`iris.random_seed` in `examples/iris_pipeline`, RFC 0004:581,
  :651). An output built once is read without a pin through any declaration
  (RFC 0004:336, RFC 0007 §3).
- ~~**One result, two names.**~~ **Settled** (spec §8; §11 item 32): a
  result's name is its output's id after the driven declarations from the
  analysis it belongs to. Reached through two such chains, it is made once,
  and placed and recorded under each name, and the record at each place has
  that place's address. Undriven declarations, back-edges included
  (`iris: {path: ..}` in `examples/iris_pipeline`), never add a name: a pin
  through one names a universe of an analysis further along its reference
  (tidy-up change 32), and the root, like an analysis whose universe a pin
  names, is never driven in its own universes (spec §7). RFC 0004 lets one
  analysis be reached through two driven declarations (`stage.inner` and
  `inner`), and RFC 0005 §1 names a result by its chain of declarations, so
  a universe that sets `inner.d1` and `stage.inner.d2` gives `inner.out#u1`
  the records `.astra/records/u1/inner.out.json` and
  `.astra/records/u1/stage.inner.out.json`. A result with two names gets its
  statuses at each place. No name is preferred, and warning about two
  spellings is the tooling's.
- ~~`requires-python`~~ **Settled:** `>=3.10`, the first version whose
  `importlib.resources` reads namespace packages (tested while planning).
