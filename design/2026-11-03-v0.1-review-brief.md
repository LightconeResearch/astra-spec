# v0.1 schema and specification: review brief

- **For:** a fresh session reviewing the v0.1 schema and specification before
  work on astra-tools starts.
- **Branch:** `v0.1-schema` of `astra-spec`, which forked from `main` at
  `1bc6eb8`.
- **Written by:** the session that designed and built it. It is
  deliberately not that session's review.

## The goal

A thorough, independent review of the v0.1 schema and specification. Find
what is wrong, ambiguous, inconsistent or missing before the tools are built
on it. Every finding must be **verified**: reproduced, with a concrete file,
command or example. A suspicion that can't be shown isn't reported.

This is a review, not a fix. Write the findings file (see *Output*) and
change nothing else. Tom decides what gets fixed.

## Settled: don't re-argue

These were decided on purpose. Challenge one only with a **concrete defect**:
a file that can't be expressed, a contradiction, or two validators
disagreeing. A preference for another approach is not a defect.

- **D1:** the generated JSON Schema (draft 2019-09) is the contract, and
  LinkML is its source.
- **D2:** everything referenced by id is a map keyed by id. Lists are used
  only for genuine lists.
- **D3:** the generator extension adds `propertyNames` to every map, allows
  one written form per map entry, adds `uniqueItems` to lists of strings,
  prunes unreachable `$defs`, and keeps only standard keywords at the top
  level.
- **D4:** element ids are LinkML `key`s. `Environment.iri` is the only
  `identifier`.
- **D5:** one id grammar, with no reserved words. Ids that one field could
  name must be distinct.
- **D6:** no `Analysis.id`.
- **D7:** the package ships only artefacts, with no Python and no
  dependencies. **D8:** fields are defined in LinkML, and the specification
  carries the concepts, grammars and catalogue.
- **D9:** one rule catalogue: codes, layers and levels.
- **D10:** the record's field is `spec_version`. A closed and an open record
  schema.
- **D11:** a named type exists only if more than one field uses it.
- **D12:** no `null` for optional fields.
- **D13:** `rules.json` is derived from spec §9, which stays the hand-written
  source, plus an error map from the schema's `rule` annotations, keyed by
  absolute keyword location.
- **Patterns:** they end in `$(?!\n)` and use explicit character classes, so
  Python and ECMA-262 agree (R5, R7).
- **YAML:** files are YAML 1.2 under the core schema only (R19).
- **Out of scope:**
  - `when` semantics (#93);
  - citing insights;
  - recipes (`Recipe`, `Resources`, `container` untouched);
  - every docs page except `docs/specification.md` (they are stale by
    design);
  - astra-tools and astra-typescript;
  - the validator/check/runner conformance suite.

## Known already: don't report as new

These are recorded in design §12 ("Deferred from the reviews") and §13
("Open points"). Read both. The open points are:
- agreeing spellings of one decision;
- an analysis with no decisions reading a per-universe output;
- one result with two names.

Report one of these only if you find it worse than recorded, or wrongly
described.

## The lenses

Run each lens as an independent pass, in parallel if you can, so that no
pass anchors on another's conclusions. Then verify every finding (next
section) before it goes in the report.

1. **RFC fidelity, blind.** Re-derive what RFCs 0003–0007 and the tidy-up
   RFC require, from the RFC texts alone. Then check the specification and
   the schema against your list.
   - Look for something required but missing, something present that no
     source asks for, and something whose meaning has changed.
   - Don't use design §10's traceability table until afterwards. Then
     compare: a row it marks as landed that doesn't land is a finding.
2. **The specification as an implementer reads it.** Give this pass only
   `docs/specification.md`, `src/astra/schema/generated/rules.json` and the
   generated JSON Schemas. Answer, with a worked example each, the questions
   a validator or checker author meets:
   - how an address and a pin resolve through declarations;
   - how an effective selection is built;
   - when an output is built per universe or built once;
   - what `NOT_BUILT_IN_UNIVERSE` and `UNDRIVEN_DECLARATION` mean for a stack
     of three analyses;
   - where a record goes, and when a result is `stale`;
   - how a JSON Schema error maps to a code, in Python and in Ajv.

   Every point where the text has to be guessed, read two ways, or
   contradicts itself is a finding.
3. **The specification as an author reads it.** From the specification
   alone, write three or four new, realistic `astra.yaml` analyses that are
   unlike the examples:
   - a single analysis with conditional decisions;
   - a driven pipeline of two analyses;
   - an analysis that reads another from a commit;
   - an analysis with findings that cite pinned results.

   Validate them against the contract (as in *Commands* below). Findings:
   - anything the format can't express that it should;
   - anything that is valid but wrong by the RFCs;
   - anything invalid that should be valid;
   - errors that are hard to understand or don't point at the cause;
   - places where the specification wasn't enough to write the file.
4. **Internal consistency.** The specification, the LinkML descriptions,
   the generated contract, `rules.json`, the fixtures, the examples and
   `CLAUDE.md` must say the same thing:
   - every rule's wording and level;
   - every field's meaning and requiredness;
   - every pattern;
   - every example in the specification (does it validate?);
   - every cross-reference and link.
5. **Standards and best practice.** Check against:
   - LinkML 1.12.1: `key` vs `identifier`, `structured_pattern`,
     annotations, class rules;
   - JSON Schema 2019-09: `$id`, `$defs`, absolute keyword location,
     `oneOf`, `if`/`then`;
   - YAML 1.2.2's core schema;
   - RFC 2119/8174: keywords normative only in capitals, and their use;
   - RFC 5234 ABNF (check the §4 grammar);
   - W3C PROV-O and Web Annotation, the mappings in the record and the
     selectors.

   Look things up rather than recalling them, and cite what you find.
6. **Edge cases and adversarial inputs.** Look for inputs that break the
   contract, that the contract wrongly accepts, or that make validators
   disagree:
   - Python `jsonschema` against Ajv 8 (`ajv/dist/2019`);
   - a strict YAML 1.2 loader against the YAML 1.1 behaviour of PyYAML;
   - Unicode, whitespace, very long or deeply nested values, and empty
     collections;
   - keys that look like numbers or booleans;
   - every pattern at its boundaries.

## Verifying a finding

Before a finding goes into the report:

- **Reproduce it:** a command and its output, a minimal document and the
  validator's verdict, or exact quotes of the passages that contradict each
  other, with file:line.
- **Check it isn't settled or known** (the two sections above).
- **Try to refute it.** If a careful reading of the RFC, the design or the
  specification answers it, drop it, or report it as Minor wording if the
  answer was hard to find.

Unverified suspicions don't go in the report. List them separately at the
end as "Not verified", one line each, with what you would need to settle them.

## Severity

- **Critical:** the contract is wrong. A valid file by the RFCs is rejected,
  an invalid one is accepted, or validators disagree on a realistic file. Or
  the specification says something false.
- **Important:**
  - an ambiguity that two implementers would resolve differently;
  - an inconsistency between two normative sources;
  - a missing rule or code;
  - a test or check that can pass for the wrong reason.
- **Minor:** wording, clarity, polish, or an example that could be better.

## Output

Write `design/2026-11-03-v0.1-review-findings.md` on `v0.1-schema`:

- a short summary: counts by severity and lens, and the three findings that
  matter most;
- the findings, most severe first. Each has:
  - an id, the lens, the severity and file:line;
  - what is wrong;
  - the evidence that verifies it;
  - why it matters (who it bites);
  - a suggested fix, one or two lines; Tom decides;
- "Considered and set aside": things you looked at and judged fine, or
  settled or known, one line each. This shows the coverage;
- "Not verified", as above.

Commit only the findings file, with a message ending in the
`Co-Authored-By` line your session uses. Don't change anything else.

## Commands

This machine runs NixOS, so `uv`, `just` and `node` aren't on `PATH`.

- Run the suite: `nix shell nixpkgs#uv nixpkgs#just --command just test`
  (drift check, pytest, lint: 361 passing at the time of writing).
- Validate a document as a consumer would. In
  `nix shell nixpkgs#uv --command uv run python`, load the YAML with the
  harness loader (`tests/conftest.py: load_yaml`) and use
  `jsonschema.Draft201909Validator` with
  `src/astra/schema/generated/analysis.schema.json`, or
  `provenance.schema.json` for a record. `tests/conftest.py` also has
  `validator(...)`, `errors(...)` and `absolute_keyword_location(...)`.
- Cross-check in JavaScript: `nix shell nixpkgs#nodejs --command …`, with
  Ajv 8 (`ajv/dist/2019`, `allErrors: true`, `verbose: true`) and the `yaml`
  package (YAML 1.2), installed in a scratch directory and never in the
  repository. Spec §10 gives the method for mapping an Ajv error to a code.
- Keep all scratch work outside the repository, in your session's
  scratchpad.
