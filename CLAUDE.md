# ASTRA Spec - Development Notes

## Schema and specification

The ASTRA schema is written in LinkML, in four modules under `src/astra/schema/`:

- **`types.yaml`** — the named types: `id`, `address`, `reference`, `option_reference`, `condition`, `commit_id`, `content_hash`, `spec_version`, `timestamp`, `iri`. The id grammar is written once, in `settings`, and the `structured_pattern`s are built from it.
- **`analysis.yaml`** — the analysis document, `astra.yaml` (`tree_root: Analysis`): inputs, outputs, recipes, decisions and options, universes and imports of other analyses' universes, declarations of other analyses.
- **`insight.yaml`** — insights and evidence, with the W3C Web Annotation selectors.
- **`provenance.yaml`** — the provenance record of a result (`tree_root: ProvenanceRecord`), mapped onto PROV-O.

The LinkML descriptions are the normative definitions of the fields: the field reference (`docs/elements/`) is generated from them, and the specification doesn't restate them. Write each description in one or two sentences, in the present tense, saying what the field is and what it takes. Descriptions carry no history: no "no longer", "was" or "replaces".

**`docs/specification.md`** is the normative specification, in four sections after a short introduction: Elements (what an `astra.yaml` holds, each element with a YAML snippet of one running example), Results (what is built, the record of each result, and how a checker compares records with the analysis), Rules (every rule, in one codes table, then the recommendations and the permission that no tool checks) and Schema files (the generated files). Each rule is stated once, in the codes table, whose columns are Code, Level and Rule: a layer row, its Code cell in bold and its other cells empty (`| **parse** | | |`), sets the layer of the rows below it; a rule with several cases has one row per case, consecutive, with one code and one level; and a check row's Rule cell ends with `→` and the status a broken rule gives. The specification changes whenever a rule or a concept does. The codes table stays hand-written, and is also data: `generated/rules.json` is extracted from it (see below), so keep its columns, its layer rows and each check row's `→`. The longer version it replaced, with its Parts, numbered sections and annexes, is at `ce3ba31:docs/specification.md`; "spec Annex A", "spec Annex D" or a "spec §" in the tests' and tools' docstrings and below refers to that version.

Schema conventions (the contract tests check the maps and the patterns):

- Every element referenced by id is an entry of a map keyed by its id. The class has a key slot, `id` with `key: true` and `range: id` (`DecisionSelection` is keyed by `decision`, an `address`), and the map is a `multivalued: true` + `inlined: true` slot. A list of objects is `multivalued: true` + `inlined_as_list: true`. Element ids are `key`s, never `identifier`s; `Environment.iri` is the only `identifier`.
- Patterns are ECMA-262 regular expressions, as JSON Schema reads them. The tests match them as ECMA-262 does (`ecma_262` in `tests/conftest.py`, which reads each `$` outside a class as the end of the value), so a pattern keeps to what ECMA-262 and Python's `re` otherwise read alike, which `ecma_262` checks: explicit classes (`[0-9]`, `[^/]`, `[^\x00-\x20\x7f]`) rather than `.`, `\s`, `\S`, `\d`, `\w` or `\b`, and no lookbehind or named group.
- A named type in `types.yaml` exists only if more than one field uses it; a pattern used once is written on its field.
- Module headers keep the placeholder `version: 0.0.0` (see Release).

The other docs pages (`docs/index.md`, `docs/getting-started.md`, `docs/llms.txt`) and `README.md` are to be kept consistent with the specification. The CLI reference and the installation page live in astra-tools, beside the code they describe, so they are never committed or edited here: the docs build (`_docs-tools`) copies astra-tools' `docs/cli.md` and `docs/installation.md` into `docs/`, from astra-tools at the justfile's `tools_ref` (overridden by `ASTRA_TOOLS_REF` and the deploy workflow's `tools_ref` input), or from the local folder `ASTRA_TOOLS_DOCS` names, to preview them (`ASTRA_TOOLS_DOCS=../astra-tools/docs just docs-serve`). `docs/llms.txt` is the agent-facing briefing served at `/latest/llms.txt` ([llms.txt convention](https://llmstxt.org/)), and is also shipped inside the wheel as `astra/docs/llms.txt` (hatch force-include in `pyproject.toml`) so that `astra guide` in astra-tools can print the copy matching the installed schema.

## The generated contract

The JSON Schemas generated from the LinkML sources are the contract: what validators in any language (astra-tools, astra-typescript, editors) check documents against. They live in **`src/astra/schema/generated/`** and are committed:

- `analysis.schema.json` — `astra.yaml`, closed
- `provenance.schema.json` — a record, closed
- `provenance.open.schema.json` — a record, open (for checkers reading records of a greater minor version than their own)
- `provenance.context.jsonld` — the record's JSON-LD context, mapping its terms onto PROV-O, with every IRI written in full and no term a prefix, so that a record's RDF (JSON-LD 1.1 toRdf with this context, plus each node's class URI) reads an environment's `iri` exactly as written. There is no context for `astra.yaml`: LinkML's flat context would give its id-keyed maps a wrong RDF reading
- `rules.json` — the rule catalogue (design D13): `rules`, every rule of the specification's codes table in document order (`code`, `layer`, `level`, `statement`, its rows' Rule cells joined with `; `, and `status` in the check layer), and `errors`, the code of every keyword of the three JSON Schemas whose error can make an instance fail, keyed by its absolute keyword location (`<$id>#<JSON Pointer>`). The tests check fixtures through it, as astra-tools and astra-typescript do

Each JSON Schema's `$id` is `https://w3id.org/astra/`, the series of the version it was generated with, `/` and its file name. The series is `X.Y` for a release `X.Y.Z` (every patch of a minor version shares its ids: a patch release never changes what is valid), a pre-release's whole version (`0.1.0rc1`), or `dev` between releases. The generator fills in the `{series}` placeholder of `--id`, and `rules.json`'s keys take the series through `$id`.

After any change to a schema module, run `just gen-schema` and commit the regenerated `src/astra/schema/generated/` with the change. Never edit these files by hand. `just check-generated` regenerates into `tmp/` and fails on any difference from what is committed; it is part of `just test` and CI. The generators stamp the version into each JSON Schema's `$comment` and `rules.json`'s, and its series into each `$id`: `$RELEASE_VERSION` when set, otherwise the tag at HEAD, otherwise `dev`. So main holds `dev`, and the drift check needs the tags fetched only at a tagged commit.

The JSON Schemas are built by **`tools/jsonschema_generator.py`**, a small extension of LinkML's `JsonSchemaGenerator` (dev-only, LinkML pinned in the dev group). It adds `propertyNames` with the key's pattern to every id-keyed map and allows one written form per map entry: an object without its key, or, for a keyed class with exactly one other slot, the compact form, that slot's value (in this schema only `DecisionSelection`, so `Universe.decisions` is `<decision>: <option>`). An import in `universes` is an object too, `{analysis: catalog, universe: alone}`: it is told from a universe by its fields, which `Universe`'s class rules check (`INVALID_IMPORT`), never by its JSON type. It also adds `uniqueItems` to every list of strings, drops every `$defs` entry the root can't reach, and keeps only standard JSON Schema keywords at the top level: LinkML's `metamodel_version` goes, and the schema version moves into `$comment`. Last, it moves each class-level check (the `oneOf` of an `exactly_one_of`, then each class rule's `if`/`then`) into its own member of `allOf`, guarded by an `if` that the value is an object and each field the check reads has its JSON type: a check is skipped only where a `type` keyword already fails, so no verdict changes and a value of the wrong type is `WRONG_TYPE` alone. Each `required` in a check has its fields in a `properties` beside it, inside a `not` too, so that Ajv compiles the schemas under `strict: true`: `just check-ajv` checks it, with the Ajv pinned in `tools/ajv/`, and CI runs it. The record's JSON-LD context is built by **`tools/jsonld_context.py`**: LinkML's (`gen-jsonld-context`'s generator), post-processed. It drops the prefix terms (`astra`, `prov`, `xsd`, …) after writing every `@id` and `@type` as a full IRI, and adds `"@version": 1.1`, so that no term is a prefix (an `iri` such as `prov:env:1` stays as written) and a JSON-LD 1.0 processor, which would read any term as a prefix, rejects the context.

`rules.json` is built by **`tools/rules.py`**, from the specification and the generated JSON Schemas with their LinkML sources; never edit it, and never write the codes table from it. Its extractor, `extract_rules`, reads the codes table with `markdown-it-py` (dev-only, never regular expressions), as CommonMark with GFM tables, and is strict, as its docstring says: no `## Rules` heading or more than one, a codes table (one whose first column is Code) outside that section, or a second one, columns other than Code, Level, Rule, a layer row whose first word is no layer (`parse`, `schema`, `validator`, `check` or `runner`), or whose other cells aren't empty, a rule row before any layer row, a row that doesn't write one cell per column (counted on its source line, blockquote markers aside), an empty cell, a malformed code, a code whose rows aren't consecutive under one layer row, rows of one code with two levels or two statuses, an unknown level (a level is `MUST` or `SHOULD`), a check row without exactly one `→` (in its text, outside emphasis and links, with text on each side) or another row with one, a Rule cell of more than one sentence (as the cell reads once rendered, outside its code spans, a `.`, `?` or `!` followed by white space, even after a closing bracket or quote), a rule whose RFC 2119 keyword contradicts its level (in its text, in a code span, or as the cell reads once rendered), a cell holding anything but text, code spans, emphasis, links and inline HTML, or a statement or status whose Markdown can't be rebuilt from its tokens, fails `just gen-schema`. A rule's `statement` is its rows' Rule cells, each check row's without its `→` and status, joined with `; `; its `status` is the text after the `→`. The recommendations table isn't read. The error map walks each JSON Schema and fails on any keyword it can't give a code, on any code that isn't a schema-layer rule of the specification, on any default code that isn't one either, and on any `rule` annotation that gives no keyword its code.

**Codes on constraints.** Each constraint in the LinkML sources names the rule it enforces with one annotation key, `rule`: `annotations: {rule: INVALID_COMMIT}`. It goes where the constraint is defined:

- on a type, for its pattern (`commit_id` → `INVALID_COMMIT`);
- on a slot, for the pattern the slot writes itself (`Input.path` → `INVALID_PATH`). A slot that writes its own pattern must have one. A map key's slot, which takes its type's pattern, may have one, which then wins over the type's (`DecisionSelection.decision`: a bad key is `INVALID_ID` whatever its type); any other slot of a named type takes its type's code (`TYPED`, below);
- on a class rule (`rules:` entry), for the `if` and the `then` of its `allOf` member;
- on each branch of an `exactly_one_of`, the same code on every branch (its `allOf` member's `if`, `oneOf` and branches take it): LinkML 1.12.1 can't annotate the `exactly_one_of` list itself.

Every `rule` annotation must give some keyword its code: one on a class, an enum, a type no slot uses, or a slot with no pattern fails the build. Keywords whose code never varies take a default instead: `required` outside a rule (`MISSING_FIELD`); `additionalProperties: false` (`UNKNOWN_FIELD`); `type` (`WRONG_TYPE`); `minProperties`/`minItems` of 1 (`EMPTY_COLLECTION`; any other minimum has no code and fails the build); `uniqueItems` (`DUPLICATE_ENTRY`); `enum`/`minimum` (`INVALID_VALUE`). The annotations don't reach the JSON Schemas.

**To add or change a rule:** edit its row in the codes table of `docs/specification.md` (a new rule goes under the layer row of its layer, and a case of a rule in a row of its own, just after the rule's other rows); for a schema-layer rule, annotate the constraint that enforces it (above); then run `just gen-schema` and commit `generated/rules.json` with the change. Every schema constraint needs a row in `NEGATIVE` (`tests/test_constraints.py`, below), and a new schema-layer code also needs an invalid fixture.

The package ships only artefacts: the LinkML sources and `generated/`, as the namespace package `astra.schema` (plus `astra/docs/llms.txt`). There are no Python files under `src/astra/` and no runtime dependencies; build-time Python lives in `tools/`.

## Tests

`just test` runs the drift check (`check-generated`), pytest and `linkml-lint`; `just check-ajv` (in CI, and wherever node is installed) compiles the three JSON Schemas with the pinned Ajv under `strict: true`. Everything is validated as a consumer would: a `jsonschema` Draft 2019-09 validator against the committed generated schemas, with each `astra.yaml` read by `load_yaml` in `tests/conftest.py` as spec Annex A reads it: by ruamel.yaml's stock parser, `YAML(typ='safe', pure=True).parse()`, given the file's bytes as they are, with no subclass or patch (never PyYAML, never LinkML's validators or Python models), and ASTRA's rules checked on its events. On the events: any error the parser raises; at most one document; each scalar read under the core schema, a plain one by YAML 1.2.2 §10.3.2's table; only the core schema's tags, each on a node of its kind (`!` reads as a string, a list or a map); every number finite; and each alias read as the node it names, one inside that node having no JSON value. On the tree, once the whole file has parsed: every key a string, and no two equal keys in one map. A broken rule raises a `YAMLError`. YAML's own grammar is the parser's to read, and the harness neither corrects nor tests it: `tests/test_loader.py` tests ASTRA's rules only, and where stock ruamel reads a file otherwise than YAML 1.2.2 (it refuses a tab as white space, a C1 control or DEL in a quoted scalar, UTF-32, and UTF-16 without a byte order mark, opens a document on a `...` with no document before it, reads NEL and U+2028 as line breaks, and takes U+FEFF in a plain scalar), the case isn't tested, here or in the conformance suite, since nobody writes such a file. Records are read as spec Annex A reads them, by `load_json` in `tests/conftest.py`: strict UTF-8, then `json.loads` with hooks that refuse a repeated name (`DuplicateNameError`) and `NaN` and `Infinity`, which `json.loads` would read, raising a `JSONError`; the specification's JSON blocks are read the same way. Numbers are held as Python holds them, so a float beyond a double's range reads as an infinity. `tests/test_provenance.py` reads records as RDF as spec Annex D says, with rdflib's JSON-LD parser (dev-only) and the committed context. `tests/test_rules.py` applies spec Annex D's filter ("From an error to its code") to the standard output of jschon (dev-only, pinned) for each schema-layer invalid fixture, and checks that every error it keeps has an entry in `rules.json` and that it gives `jsonschema`'s (pointer, code) pairs. The validator, `Validator` in `tests/conftest.py`, matches each `pattern` as ECMA-262 does (`ecma_262`): `jsonschema`'s own `pattern`, like jschon's, uses Python's `re`, whose `$` also matches before a final newline, so no invalid fixture's point is a value ending in one.

Fixtures are whole documents in `conformance/documents/valid/` and `conformance/documents/invalid/`, and, for an invalid one whose break is in a `when`, in `conformance/documents/when/invalid/`, kept apart since `when` may leave the specification (issue #93); `fixtures` in `tests/conftest.py` lists both folders' fixtures. They are the conformance suite's documents, which other implementations read too, named `Analysis-<nnn>-<what>.yaml` (an `astra.yaml`) or `ProvenanceRecord-<nnn>-<what>.json` (a record): the root picks the schema, and `<nnn>` numbers from `001` for valid fixtures, from `101` for invalid `Analysis` fixtures and from `201` for invalid `ProvenanceRecord` fixtures. Each invalid fixture is a minimal valid document with one thing broken, and starts with two comment lines (and a third, `# also:`, where its one break brings a second error; see below). A record can't hold a comment, so its lines are in a sidecar, `ProvenanceRecord-<nnn>-<what>.header`, which every invalid record has and a valid one may have for a note:

```yaml
# rule: <CODE>          a code from the specification's codes table
# fails at: <location>  a JSON Pointer, `(root)` for the document, or `parse`
```

The test (`check_invalid_fixture` in `tests/test_fixtures.py`) asserts that the fixture fails for the right reason: the validator reports errors at that location and nowhere else, and `rules.json` gives those errors the fixture's rule, through each error's absolute keyword location (`absolute_keyword_location` in `tests/conftest.py`: the JSON Pointer of `error.schema`, found in the schema by identity, then `/` and `error.validator`, since `jsonschema`'s `schema_path` runs through `$ref`s). A `parse` fixture's loader error must give exactly its code (`parse_code`: `INVALID_SYNTAX`). Where the one break also brings an error somewhere else, the fixture declares it in a third comment line, `# also: <CODE> at <pointer>`: the errors at that pointer must then be reported, and `rules.json` must give them that schema-layer code; no other second error is allowed, and a `parse` fixture has no `# also:` line. `jsonschema` reports each kind of error here:

| What fails | Location |
|---|---|
| missing field, unknown field, `exactly_one_of`, class rule | the object |
| bad map key, empty map | the map |
| empty list, repeated entry | the list |
| wrong value or wrong type | the value |

Every parse- and schema-layer code in the catalogue has at least one invalid fixture, and every schema constraint a row in `NEGATIVE` (below). `Analysis` fixtures that check-yaml or yamllint refuse, valid or not (malformed YAML, say), are kept out of the repository's YAML linters, through lists kept by hand: add each new one to `check-yaml`'s `exclude` in `.pre-commit-config.yaml` and to `ignore` in `.yamllint.yaml`. A fixture whose tab or lone CR is its point also goes in the `exclude` of the `end-of-file-fixer` and `trailing-whitespace` hooks. One whose point is that it ends with no line break goes in the `end-of-file-fixer`'s `exclude`, has a section of `.editorconfig` that sets `insert_final_newline = false`, and turns yamllint's `new-line-at-end-of-file` off in a comment. Record fixtures are `.json`, which those linters don't read. Every `astra.yaml` under `examples/` must also validate, and the specification's YAML and JSON blocks are checked (`tests/test_specification.py`), once their placeholders (`<commit id>`, `sha256:<hash>`, `<size>`, `<url of a git repository>`) are filled: a whole document (one with `spec_version`) validated, any other block, part of an `astra.yaml`, validated over a stub, and one that leaves fields out on a line `...` validated over the stub but for the required fields it leaves out.

The conformance suite's analysis cases (`conformance/analyses/`) are git repositories for a validator to judge. astra-spec has no validator, so `tests/test_conformance.py` checks only that each case is laid out and builds as `conformance/README.md` says, that its `files/` holds no `.gitignore` and nothing astra-spec's `.gitignore` ignores, that its `expected.json` follows `conformance/expected.schema.json`, names rules of `rules.json`, and gives a pointer only for a parse or schema code, and that the cases that use `when` are those in `conformance/analyses/when/`.

One code covers many keywords, so the constraints are pinned one by one, by cases written by hand, never read from the sources or the generated schemas, which a loosened constraint would change too. In `tests/test_constraints.py`, each row of `NEGATIVE` is a valid fixture, a JSON Pointer, an edit (a value set there, or `DELETE`) and a code: the edited document must fail where the row says, with that code, and nowhere else, as an invalid fixture must (`check_schema_errors`), and a record's row also against the open schema, which accepts a row's unknown field (`UNKNOWN_FIELD`) instead. Its meta-tests check that the rows reach every keyword of each schema's error map and every field of every `required`, so a new constraint needs a new row. `FACETS` there gives each pattern a slot writes itself values it accepts and values it rejects, one for each facet its description states, as `tests/test_types.py` does for the named types. `TYPED` in `tests/test_contract.py` gives each slot of a named type its type, whose pattern and code the slot must have, and every map key takes `id`'s (`address`'s in `Universe.decisions`) and `INVALID_ID`.

The site renders the specification with Python-Markdown, not CommonMark, so `tests/test_site.py` reads the built page (`site/specification/index.html`) and checks that the codes table shows each rule of `rules.json` as it words it, rendered by markdown-it: its code and level, each under the layer row of its layer, and its rows' Rule cells, joined, its statement and, after each `→`, its status; the table is under the Rules heading, and every in-page link resolves. It also checks the field reference: `gen-doc` writes a pattern as a Markdown code span, which a backtick or `|` in the pattern breaks, so `just gen-doc` rewrites each Regex Pattern cell as `<code>`, every character but an ASCII letter or digit as a numeric character reference (`tools/pattern_cells.py`), and the test checks that each element's page shows the pattern exactly as the LinkML sources write it. It checks too that the index cuts each description at the end of a sentence or of a word, in at most 80 characters, and lists the record's classes apart, that each range links to a class, an enumeration or a type, that no two pages' names differ only in case (`tools/docgen.py`), that `command`'s page shows its `<entry>` placeholders, and that the merged models in `docs/schema/` hold every class. `just docs-strict` builds the site with `zensical build --strict`, which fails on any issue. CI's docs builds (`main.yaml`, `test_pages_build.yaml`) run the test after `just docs-strict`; it is skipped wherever there is no `site/`.

## Documentation versioning (mike)

The whole docs site is versioned with [mike](https://github.com/squidfunk/mike) — specifically squidfunk's fork, which Zensical's versioning provider depends on. Each release deploys a full copy of the site to a subdirectory of the `gh-pages` branch (`/0.0.9/`, `/latest/`, etc.). Mike is enabled via `[project.extra.version] provider = "mike"` in `zensical.toml`; the version dropdown in the header is rendered natively.

Release flow:

1. `just release X.Y.Z` — regenerates the contract with the release version (`RELEASE_VERSION=X.Y.Z just gen-schema`), updates `CITATION.cff`, commits both (`src/astra/schema/generated/` and `CITATION.cff`), and creates an annotated tag; then regenerates the contract as `dev` and commits it ("Back to dev after vX.Y.Z"), so that only the tagged commit holds the version. Does not push. The version may be a pre-release, `X.Y.Z` followed by `aN`, `bN` or `rcN` (PEP 440's normal form, so the tag `v0.1.0rc1`, the wheel and the `$id`s agree); its ids carry its whole version, and the documents it checks still state `spec_version: "0.1.0"`. A patch release never changes what the schemas accept, and a change to what is valid waits for the next minor version: when the version's minor already has a release (from 0.1 on), `tools/check_patch.py` compares the regenerated JSON Schemas (descriptions, titles and comments aside) and `rules.json`'s `errors` (keys and codes) with that minor's greatest release, and the release fails before it commits on any other difference. Schema YAMLs are *not* mutated: they keep the placeholder `version: 0.0.0`, and the generators read a staged copy under `tmp/schema/` with the version injected, from `$RELEASE_VERSION`, else the tag at HEAD, else `dev`.
2. `git push --atomic origin HEAD vX.Y.Z` — review, then push the two commits and the tag together. The `Deploy versioned docs on tag` GitHub Actions workflow deploys the docs automatically: a release `X.Y.Z` at `/X.Y.Z/`, moving the aliases `X.Y` and `latest` (`mike deploy --push --update-aliases X.Y.Z X.Y latest`); a pre-release at its own version, moving none. A GitHub release marked as a pre-release still publishes to PyPI, where pip skips it unless asked.

For a manual deploy (e.g. backfilling a tag), `just docs-deploy X.Y.Z X.Y latest` (or `just docs-deploy 0.1.0rc1` for a pre-release), run at a checkout of the tag `vX.Y.Z`, runs the same `mike deploy` locally. It refuses at any other commit, since the site publishes the checkout's committed contract and main holds `dev`; a dispatch of the workflow checks out the tag of its version for the same reason.

First-time setup: after the first deploy, run `just docs-set-default latest` once so the bare site root redirects to `/latest/`.

Hosting: mike pushes to `gh-pages`. The hosting platform (Cloudflare Pages, GitHub Pages, etc.) must be configured to serve from `gh-pages`, not `main`. Without this, `mike deploy` runs successfully but the site doesn't pick up versioned URLs in production.

Schema artifacts (`docs/schema/*.{yaml,json,jsonld}`) are versioned along with the rest of the site: `just gen-doc` writes the merged LinkML models there (`astra.yaml` for the analysis document, `provenance.yaml` for the record) and copies in the committed contract from `src/astra/schema/generated/`. Machine consumers should resolve them via the canonical `https://w3id.org/astra/X.Y/...` URI of their minor version (which redirects to the `X.Y` alias's `schema/`, the latest patch's files), or pin to `astra-spec.org/X.Y/schema/...` for a minor version, or `astra-spec.org/X.Y.Z/schema/...` for one release.

## Key Commands

```bash
just test             # Drift check of the generated files, pytest, and linkml-lint
just gen-schema       # Regenerate the contract into src/astra/schema/generated/ (commit it)
just check-generated  # Fail if the committed generated files differ from a fresh generation
just check-ajv        # Compile the three JSON Schemas with the pinned Ajv under strict: true (needs node)
just lint             # Lint the schema (linkml-lint)
just gen-doc          # Generate the field reference (docs/elements/) and docs/schema/
just docs-serve       # Build and preview docs locally with live reload
just release X.Y.Z    # Regenerate the contract with the version (patch guard), update CITATION.cff, commit, tag, back to dev
```

## Repository Layout

- `src/astra/schema/` — LinkML schema sources: `types.yaml`, `analysis.yaml`, `insight.yaml`, `provenance.yaml` (edit these)
- `src/astra/schema/generated/` — The generated contract: the JSON Schemas, the record's JSON-LD context and `rules.json` (regenerate with `just gen-schema`, commit, never edit)
- `tools/jsonschema_generator.py` — The JSON Schema generator extension
- `tools/rules.py` — Builds `rules.json`: the codes table's extractor and the error map
- `tools/jsonld_context.py` — Builds the record's JSON-LD context: LinkML's, with every IRI in full and no term a prefix
- `tools/check_patch.py` — The patch guard of `just release`: a patch changes nothing valid since its minor's greatest release
- `tools/pattern_cells.py` — Run by `just gen-doc`: writes each Regex Pattern cell of the field reference as HTML, so that the site shows the pattern exactly
- `tools/docgen.py` — Run by `just gen-doc` in place of LinkML's `gen-doc`: each description in a table cut at the end of its first sentence, or of a word within 80 characters; ranges linked to their type's page; `<` and `&` shown as written; and a `-slot` suffix on a slot's page whose name differs from another page's only in case
- `linkml-templates/` — The field reference's templates for the index, type and slot pages
- `tools/ajv/` — A pinned Ajv (`package.json`, `package-lock.json`) and `check.mjs`, for `just check-ajv`
- `docs/` — Documentation source (rendered with [Zensical](https://zensical.org/); config in `zensical.toml`)
- `docs/specification.md` — The normative ASTRA specification
- `docs/index.md` — Landing page (clean, MCP-style with card grid nav)
- `docs/getting-started.md` — Install + scaffold + validate tutorial
- `docs/cli.md`, `docs/installation.md` — astra-tools' CLI reference and installation page, copied from astra-tools by the docs build (`_docs-tools`, not committed)
- `docs/elements/` — Auto-generated schema reference (generated by `just gen-doc`, not committed)
- `docs/schema/` — Published schema artifacts (written by `just gen-doc`, not committed)
- `examples/` — Example ASTRA projects (iris, iris_pipeline)
- `conformance/` — The conformance suite, for any implementation (see `conformance/README.md`)
- `conformance/documents/valid/`, `conformance/documents/invalid/` — Fixtures, validated through the committed JSON Schemas (`conformance/documents/when/invalid/` holds the invalid ones whose break is in a `when`)
- `tests/generator/` — Scratch schemas for the generator extension's and the named types' tests
- `rfcs/` — ASTRA RFCs, the record of significant changes to the specification
